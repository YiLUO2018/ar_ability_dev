# gpu_on_phone 设计文档

> 状态：现行基础（v0.1）｜日期：2026-10-14
> 本项目为**探索/基础设施项目**：不做业务功能，产出 = 基准 App + 可复用推理封装 + 选型结论。

## 1. 项目定位与动机

**探索手机端 GPU（及配套加速单元）对模型推理的利用，优化推理速度，沉淀成其他项目可直接复用的结论与封装。**

直接动机（2026-10 现状痛点）：
- 象棋教练 App 的 **EdgeSAM 定位在真机 CPU 上单次 ~1s**（encoder 22MB + decoder 16MB，ONNX Runtime 1.22.0 CPU EP）→ 检测率仅 ~1Hz，是棋盘跟随慢的根源；PC CPU 同模型 ~0.5s/帧，端侧已优于预期但仍不达标。
- 眼球追踪 App 阶段四/五、人脸识别 App 后续都要上端侧模型，推理后端选型是共同前置问题。

**受益方**：`chinese_chess_coach_phone_version`（EdgeSAM/YOLO）、`eye_tracking_phone_version`（阶段四五）、`face_recognition_phone_version`。

## 2. 目标与非目标

**目标**
1. 在真机上对真实业务模型建立**统一、可复现的延迟基准**（分框架 × 分执行后端 × 分精度）。
2. 给出「模型类型 → 推荐后端」的选型结论表，并解释失败/负优化案例（算子回退、分区拷贝开销等）。
3. 沉淀可复用封装：其他项目拷一个模块/一组配置即可启用胜出后端。

**非目标**
- 不做业务 App（无相机/无 UI 功能，benchmark 载体除外）。
- 不自训模型、不改模型结构（量化/转换等**部署侧**处理除外）。
- 不追求全机型覆盖：首期以手头真机（V2509A）为准，结论标注适用芯片范围。

## 3. 技术候选总览

详细调研与待验证清单见 `../03-探索与调研/GPU加速候选路线.md`。此表为路线图视角的索引：

| 路线 | 框架/接口 | 加速单元 | 备注 |
|---|---|---|---|
| A. CPU 基线 | ONNX Runtime XNNPACK EP | CPU | 现象棋默认 CPU EP 的对照上限 |
| B. 系统代理 | ONNX Runtime **NNAPI EP** / LiteRT NNAPI delegate | NPU/GPU/DSP（厂商驱动决定） | ❌ 已关闭（10-14）：Android 15 弃用 + 天玑生态已绕开；象棋 M1 旧 bench 仅作历史对照 |
| C. GPU 专用 | LiteRT（TFLite）**GPU delegate** | GPU（OpenCL→GL 回退） | ✅ **主线**：需模型转 tflite（PyTorch 上游）；fp16 支持好；EdgeSAM encoder 纯 CNN 算子覆盖良好 |
| C+. 厂商 NPU（新增） | **LiteRT MediaTek NPU（CompiledModel）** | 天玑 NPU | ✅ 上限路线（G2）：MT6990 官方支持；minSdk 31/量化/AOT 门槛 |
| D. 厂商专用 | ONNX Runtime **QNN EP**（高通） | Adreno GPU + Hexagon NPU | ❌ 已关闭（10-14）：V2509A 非高通 |
| E. 跨芯片 GPU | ncnn / MNN（Vulkan） | GPU（Vulkan） | 自带算子生态与转换工具，绕开 NNAPI 弃用问题 |
| F. 兜底 | 原生 OpenCL / Vulkan compute | GPU | 仅当现成框架对关键算子不达标时考虑 |

**分水岭已定（2026-10-14 调研确认，真机 getprop 待复核）**：V2509A = vivo X300 = **联发科天玑 9500（MT6990），GPU Mali-G1-Ultra**——B（NNAPI）与 D（QNN）关闭；主线 = **C（LiteRT GPU delegate）**，上限 = **C+（LiteRT MediaTek NPU，MT6990 在官方支持列表）**，E（ncnn/MNN）为「保 ONNX」备选；A（ORT CPU/XNNPACK，含 1.22→1.31 升级）为零风险基线。证据与全部细节见 `../03-探索与调研/GPU加速调研汇总（GitHub与arXiv）.md`，决策跟踪见 `../03-探索与调研/GPU加速候选路线.md`。

## 4. 基准方法学（本项目的核心资产，先于任何跑分立起来）

| 项 | 约定 |
|---|---|
| 输入 | 固定随机种子生成的张量（或固定真实帧），前后处理**分开计时**，只报纯推理 |
| 预热 | 每配置 warmup ≥5 次（剔除 JIT/懒加载），首帧（含编译/加载）**单列**——NNAPI/QNN 首次编译可达数秒 |
| 统计 | 每配置 ≥30 次，报 **median / p90 / p99**，不报均值（长尾才是体验） |
| 设备状态 | 记录电量/充电/温度（`dumpsys battery`、thermalservice），连续跑批前后各记一次；热节流时段的批次作废重跑 |
| 输出 | 每次 run 落盘 JSON（设备信息+配置+原始延迟数组）到 `bench_results/`，adb 拉回 PC 汇总；结论表进 docs |
| 公平性 | 同一 APK 内切换配置；帧间无 sleep 连发与间隔连发各测一轮（模拟真实相机帧率下的 cache 行为） |

## 5. 基准模型集（真实业务模型，不用玩具模型）

| 模型 | 来源 | 输入 | 为什么选它 |
|---|---|---|---|
| EdgeSAM encoder | 象棋 `assets/models/edge_sam_3x_encoder.onnx` | [1,3,1024,1024] fp32 | 最大痛点，重视觉主干，最值得 GPU 化 |
| EdgeSAM decoder | `edge_sam_3x_decoder.onnx` | embeddings + 动态点提示 | 小而动态形状，检验各后端对非常规输入的适配 |
| yolov8n_chess | `yolov8n_chess.onnx`（v9） | [1,3,480,640] | 常规检测头，代表多数 CV 模型形态 |
| （可选）算子覆盖参照 | 公开小模型（如 MobileNetV3） | — | 检验各后端算子覆盖/回退行为的参照系 |

模型文件不入库，放 `models/`（见其 README 记录版本与获取方式）。

## 6. 分阶段路线

| 阶段 | 内容 | 状态 |
|---|---|---|
| G0 | 基准设施：benchmark App 骨架（单 Activity + 配置选择 + 自动跑批 + JSON 落盘）、方法学落地、SoC/Android 版本确认、模型集就位 | ⬜ 当前 |
| G1 | 框架横评第一批：A（CPU/XNNPACK + ORT 升级 1.31，零风险先手）vs C（LiteRT GPU delegate，需从 PyTorch 上游转 tflite）；EdgeSAM 三件套 + YOLO 全跑；B/D 已关闭不跑 | ⬜ |
| G2 | 深入胜出路线：fp16/int8 量化（PTQ4SAM/SAQ-SAM 方法论）、C+（LiteRT MTK NPU，encoder 单独 NPU 化 + 子图回退）、算子覆盖/图分区分析；E（ncnn/MNN）视 C 转换链路受阻与否 | ⬜ |
| G3 | 沉淀复用：推理封装模块化 + 象棋 App 接入实测（定位延迟 1s → 目标 ≤200ms 量级），写集成指南 | ⬜ |
| G4 | （条件触发）现成框架全不达标时，评估 F（原生算子）或放弃 GPU 转折路线（如更小模型） | ⬜ |

**止损原则**：每阶段结束在开发日志写「继续/转向/止损」结论；单一路线投入超过预期收益（如量化精度崩坏无法修复）即记录并转向。

各阶段对应的具体实验设计、测量矩阵与裁决门见 `实验验证计划.md`（2026-10-14，全路线配实验：A/B/C/C+/E/X 共 19 项）。

│       ├── MainActivity.kt     # 跑批入口 + 结果展示/导出

├── models/                # 基准模型落盘（不入库，README 记清单）

## 8. 风险与开放问题

- **NNAPI 弃用**（Android 15+，已实证）：B 路线**已关闭**（2026-10-14）；官方继任 = LiteRT（GPU delegate + CompiledModel NPU）。
- **EdgeSAM decoder 动态输入**：点提示 [1,N,2] 可变，GPU/静态图引擎表达差——**已定为 decoder 留 CPU**（社区实测 <100ms，encoder 占 ~90% 耗时才是主战场）；静态图引擎需定长 padding 绕行。
- **小模型 GPU 负优化**：ncnn 作者明言「多数小模型 GPU 比 CPU 慢」+ iPhone LLM 0.75× 实证（arXiv:2505.06461）→ YOLOv8n 上 GPU 前必须实测，横评含同引擎 CPU 对照。
- **量化精度**：fp16 一般稳；int8 有 SAM 专用 PTQ 方案（PTQ4SAM：GELU 双峰+attention 离群两个坑都有解）；精度评估=与 CPU fp32 输出的 IoU/mAP 差，G2 先定义。
- **热节流**：不控温的 A/B 无效（arXiv:2206.10849）；持续负载吞吐可腰斩、手机 GPU 有被 OS 封顶的失败模式（arXiv:2603.23640）→ 跑批控温+逐迭代记录热状态。
- **天玑 NPU 不确定性**：MTK 侧公开跑分波动大（天玑 9400 在 AI Benchmark 成绩异常低）、9500 无公开 NPU 数据 → C+ 路线预期需保守，真机实测前不设过高目标。
