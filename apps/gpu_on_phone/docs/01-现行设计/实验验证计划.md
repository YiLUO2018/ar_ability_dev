# gpu_on_phone 实验验证计划

> 状态：现行（v1.0）｜日期：2026-10-14
> 原则：**每条可行路线都配实验，用真机数据裁决**——文献只能改先验，不能替代实测。已关闭路线中，NNAPI 因成本极低仍做一次关闭性实测；QNN 因非高通硬件物理不可测，不做。
> 前置阅读：`../03-探索与调研/GPU加速调研汇总（GitHub与arXiv）.md`（为什么是这些路线）；测量口径见 `设计文档.md §4`（本文不重复，只引用）。

## 0. 实验总览

| 路线 | 实验编号 | 核心问题 | 复杂度 | 预期产出 |
|---|---|---|---|---|
| 共享设施 | G0-1~4 | 计时/精度/落盘基础设施 + 设备能力摸底 | 中 | 可复现的横评底座 |
| A. ORT CPU | A1~A4 | CPU 极限在哪（升级/XNNPACK/fp16） | 低 | **全局分母基线** |
| B. NNAPI | B1 | 遗产路径实测是否负优化 | 极低 | 关闭性数据，归档 |
| C. LiteRT GPU | C0~C3 | tflite 转换可行？GPU delegate 加速比？ | 高 | 主线成/败裁决 |
| C+. LiteRT MTK NPU | C+1~3 | 编译模型 API 在真机可用？NPU 上限？ | 高 | 上限路线成/败裁决 |
| E. ncnn/MNN | E1~E3 | 保 ONNX 的 GPU 路线备胎成色 | 中 | 对照数据/接棒依据 |
| 公共叠加 | X1~X4 | 512 分辨率/量化/热节流/per-op | 低–中 | 可叠加收益量化 |

**执行顺序**（依赖关系）：

```
G0 ──→ A1~A4（基线）──→ B1（顺手测）
 │
 ├──→ C+1（NPU 可用性探针，早做：二值结果决定上限预期）
 │
 └──→ C0（转换 spike，关键路径）──→ C1~C3 ──→ E1~E3（最小验证）
                                        └──→ 初步胜者 ──→ X1~X4（叠加实验）──→ 终选
```

## 1. G0 共享基础设施（一切实验的前置）

**G0-1 真机能力摸底**
- `getprop`：`ro.soc.model`（预期 MT6990）/ `ro.hardware.egl`（Mali）/ `ro.build.version.release` / API level。
- GPU 能力探针：Vulkan 版本（`dumpsys vulkan` 或 ncnn 日志）、OpenCL 是否对普通 App 暴露（LiteRT GPU delegate 日志会报告选中 OpenCL 还是 GLES 回退）。
- 温控基线：`dumpsys thermalservice` 空闲态读数，确定「可测温度窗口」。
- 产出写入 `bench_results/device_profile.json`。

**G0-2 benchmark App 骨架**（单 Activity，包名 `com.arability.gpu_on_phone`）
- `bench/`：计时器（首帧单列/warmup≥5/正式≥30 次取 median/p90/p99/方差，口径按设计文档 §4）、每迭代热状态采样、JSON 落盘。
- `backends/`：统一接口 `Backend { name(); warmup(); firstRunMs(); runOnce(); }`，保证横评只换实现不换计时路径。
- `tools/`（PC 侧）：adb 拉取 + 汇总出表脚本。

**G0-3 模型集 + 测试集 + golden 参考**
- 模型拷入 `models/`（EdgeSAM enc/dec、yolov8n_chess，登记版本）。
- **固定测试输入**：从象棋 `debug_frames` 选 15 帧真实棋盘帧（覆盖正视/斜拍/角出画），每帧配 5 组固定点提示（中心±偏移）；YOLO 用同帧 480×640。输入张量打包进 assets，保证跨后端逐位一致。
- **golden 生成**：真机 ORT CPU fp32 跑一遍全测试集，输出存 `bench_results/golden/`（encoder embedding 太大就存端到端 mask 二值图 + YOLO 解码框）。

**G0-4 精度评估器**
- EdgeSAM：端到端 mask 与 golden 的 IoU（逐帧取均值）。YOLO：与 golden 的框匹配率（IoU≥0.9 且类别一致 / golden 框总数）。
- 门限（初值，可按数据调整）：fp16 档 IoU/一致率 ≥0.99；int8 档 ≥0.97。

## 2. 路线 A：ORT CPU 基线与免费优化（全局分母）

| # | 实验 | 步骤 | 裁决 |
|---|---|---|---|
| A1 | 现状基线复刻 | ORT 1.22 CPU fp32 三件套全测 | 锚定「~1s」到具体数字表 |
| A2 | ORT 升级红利 | 1.22 → 1.31 同模型同输入 A/B | 更快则全局换 1.31（预期白捡） |
| A3 | XNNPACK EP | 1.31 + `addXnnpack()` | 更快则基线配置含 XNNPACK |
| A4 | fp16 模型 | ONNX 转 fp16 × {CPU EP, XNNPACK} | 延迟+精度双达标则采纳 |

- **产出**：最终 CPU 基线配置（后续所有加速比的分母）；A 系列每步只在接受更优时保留，形成「CPU 最优栈」。
- 预期：A2/A3 有小幅度免费收益；fp16 在 CPU 上收益有限（主要给 GPU 路线铺路）。

## 3. 路线 B：NNAPI 关闭性实测（成本极低，一次做完）

**B1**：1.31 + `addNnapi()`（含 fp16 flag）跑三件套；开 ORT verbose log 记录图分区落点（哪些子图回退 CPU）。
- 测量：稳态延迟 + **首帧编译时间**（NNAPI 特有大项）+ 精度。
- 裁决：无论结果如何本路线归档关闭——若意外大幅正向（>A 系列最优），升级为「意外发现」重评（文献预期：负优化或局部加速）。
- 附带产出：把象棋 M1 期间的 NNAPI 旧 bench 结论一并搬运归档（历史对照）。

## 4. 路线 C：LiteRT GPU delegate（主线，成败在转换）

**C0 转换链路 spike（关键路径，最先做、独立成报）**
| 子项 | 内容 | 预判 |
|---|---|---|
| C0a | EdgeSAM encoder：官方 PyTorch repo → LiteRT Torch → tflite（fp32+fp16） | 静态输入 [1,3,1024,1024]，RepViT 纯 CNN，预期可行 |
| C0b | EdgeSAM decoder：同链路；动态点提示 [1,N,2] → 尝试定长 padding（N=1/2/10 三档编译） | 大概率受阻；受阻即定「decoder 留 CPU」，不算失败 |
| C0c | YOLOv8n：ultralytics 官方 `export format=tflite`（自训 v9 权重） | 官方路径，预期直接成功 |

- 每步记录：转换失败的具体算子清单（这是路线 C 最重要的情报）。

**C1 GPU delegate 横评**（同 LiteRT runtime 内对照，防引擎差异污染）
- 矩阵：{GPU delegate, CPU interpreter} × {fp32, fp16} × 三件套；序列化开/关（记初始化时间）。
- 关键观察项：GPU delegate 实际选中 OpenCL 还是 GLES 回退（日志确认）。

**C2 拆图实测**：encoder(GPU) + decoder(CPU) vs 全 CPU vs 全 GPU——验证「decoder 绕行不吃光 encoder 收益」。

**C3 精度**：G0-4 评估器全测试集过一遍。

**裁决门**：
- encoder 加速 ≥2×（vs A 系列最优 CPU）且 IoU ≥0.99 → **C 路线成立**，进入 G2 深化；
- 加速 1.2–2× → 边缘，交 X1（512 分辨率）叠加后再判；
- GPU 慢于 CPU（负优化实锤）→ 归档记录（对照 ncnn 作者警示），转 E 为主。

## 5. 路线 C+：LiteRT MediaTek NPU（上限路线）

**C+1 可用性探针（早做——二值结果，决定整个路线存亡）**
- 问题：无 PODAI/Play 分发的前提下，普通侧载 APK 里 `CompiledModel` 能否在 V2509A 上拿到 MTK NPU？（vendor runtime 是否随机预置）
- 步骤：最小 demo（单个已量化小模型走 NPU 路径）+ 官方 AI Hub/LiteRT 样例模型试跑；失败则记录失败形态（API 缺失/运行库缺失/编译失败）。
- 裁决：不可用 → C+ 归档「依赖 PODAI 分发，当前无法侧载验证」，等未来上架 Play 再议；可用 → 继续。

**C+2 encoder NPU 化**
- encoder int8（QDQ 格式，转量化用 PTQ4SAM 思路应对 GELU 双峰/attention 离群）+ AOT 与 JIT 两种编译模式各测。
- 观察算子覆盖与回退布局（目标布局：encoder NPU / decoder+YOLO 仍走胜出的 GPU/CPU）。

**C+3 终测**：稳态延迟（首帧编译时间单列，JIT 缓存二次启动也测）+ 精度（int8 门 ≥0.97）+ 与 C 路线对比。
- 裁决门：encoder ≥5× vs CPU 基线且精度过门 → 上限路线成立；否则 C 单独扛。

## 6. 路线 E：ncnn（Vulkan）/ MNN（OpenCL+Vulkan）——保 ONNX 备选

**触发条件**：C0 转换链路受阻 → E 升为主力全量投入；C 顺利 → E 只做**最小验证**（encoder 单模型），保留对照数据。

| # | 实验 | 内容 |
|---|---|---|
| E1 | ncnn 链路 | `pnnx` 转三件套（decoder 定长 padding）→ Vulkan 后端跑 encoder/YOLO；记录算子通过率与失败清单 |
| E2 | MNN 链路 | `MNNConvert` 转三件套 → OpenCL 后端（Vulkan 对照）跑 encoder/YOLO |
| E3 | 引擎内对照 | 各引擎 GPU 后端 vs 自家 CPU 后端（同引擎公平对比）；精度过 G0-4 |

- 裁决：与 C 路线同台比较（同一测试集/口径），Mali 上 OpenCL(MNN) vs Vulkan(ncnn) vs LiteRT(OpenCL/GLES) 三者见真章。

## 7. 公共叠加实验（在初步胜者上跑）

| # | 实验 | 内容 | 门 |
|---|---|---|---|
| X1 | 512 分辨率 | EdgeSAM 输入 1024→512（输出上采样回 1024 再算 IoU，公平对比）在胜出后端上 A/B | IoU ≥0.97 且延迟再省 ~3×（像素量 1/4）→ 采纳 |
| X2 | int8（GPU/CPU 路线） | 仅当 fp16 胜出后仍不达标时：PTQ4SAM 方案量化 encoder | int8 门 ≥0.97 |
| X3 | 热节流持续负载 | 胜出配置连续跑 5–10 分钟（模拟象棋 1Hz 场景加速批），延迟轨迹+温度轨迹 | 末段 median 劣化 ≤20% 视为可接受 |
| X4 | per-op 分解 | 任一「不达标/负优化」结论前必须做：ORT profile / LiteRT per-op / ncnn-MNN 日志，定位回退算子 | 产出瓶颈算子清单 |

## 8. 结果记录与决策规则

- **落盘**：每实验一 JSON（schema：`meta{device,soc,android,runtime,backend,model,precision,battery,thermal}` + `first_run_ms` + `latencies_ms[]` + `accuracy`），`bench_results/` 不入库，结论进 docs。
- **结论落点**：每实验完成后在 `../03-探索与调研/GPU加速候选路线.md` 验证状态表更新一行（成/败/数字/日期）。
- **全局决策**：所有路线测完 → 总表（路线 × encoder 延迟 × 端到端延迟 × 精度 × 首帧 × 热稳定性 × 集成成本）→ 选型写入 `00-现状/` 总结 + 更新设计文档 → G3 封装。
- **止损**：单实验连续两次受阻（转换/驱动层）即记录受阻原因转下一路线，不在同一堵墙上撞三次。
