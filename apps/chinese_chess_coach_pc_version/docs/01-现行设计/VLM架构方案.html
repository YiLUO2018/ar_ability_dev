1. 设计目标与核心思路

1.1 系统目标

基于真实象棋视频/图像，实现以下能力：

  • 视觉感知：从画面中识别棋盘角点与棋子位置
  • 局面重建：将检测结果映射为标准的 FEN 局面表示
  • 走子建议：调用 Pikafish 引擎计算最佳走法、评分与候选变化
  • 智能评论：结合局面、引擎分析、视觉场景，生成自然语言讲解与教学评论
  • 可视化渲染：将检测框、棋盘状态、推荐走法、评论文字叠加回原画面

1.2 核心设计思路

  • 共享视觉基座：图像只经过一次 Vision Encoder，检测头与语言塔共享其视觉特征，避免重复计算，保证语义一致。
  • 检测与语言双分支：检测头读取空间特征图做精确定位；语言塔读取投影后的视觉 token 做场景理解，两路适配器分离。
  • 专用模块做专用事：检测头负责"找棋子"，Pikafish 负责"算走法"，Qwen 负责"说人话"，各司其职。
  • 引擎不替代、模型不越界：不让 VLM 学下棋，而是让它编排引擎、解释结果、生成评论。
  • 分阶段训练：检测头、投影层、语言塔 LoRA 依次训练，4060 显存可控。

1.3 系统边界

模块 负责 不负责
Vision Encoder 提取通用视觉特征 不做具体检测或语言生成
棋盘角点检测头 定位 4 个棋盘角点 不识别棋子
棋子检测头（DETR） 输出棋子边界框 + 类别 不生成 FEN、不下棋
Pikafish FEN → 最佳走法 + 评分 + PV 不生成自然语言
Qwen 语言塔 局面讲解、走法解释、评论生成 不做精细定位、不做搜索

3. 模块详解

3.1 共享视觉编码器

核心：图像只经过一次编码，检测头和语言塔共享同一套视觉表征。

候选模型 特点 适用性
DINOv2 / DINOv3 自监督预训练，冻结特征质量极高，擅长密集预测 推荐（角点、边缘敏感）
SigLIP 图文对齐预训练，语义理解强 可选（语言对齐友好）
CLIP ViT 生态成熟，社区资源多 备选（分辨率偏低）
Qwen-VL 自带 ViT 与 Qwen 语言塔天然对齐 推荐（省去投影层训练）

输出格式：单尺度特征图 (B, N, D) 或 (B, D, H, W)，其中 N 为 patch 数量，D 为特征维度。

3.2 检测分支

3.2.1 检测适配层

Vision Encoder 输出的是单尺度序列特征，检测头需要 2D 空间结构或多尺度金字塔。适配层负责：

  • reshape：将 (B, N, D) 还原为 (B, D, H, W)
  • Neck：从中间层抽取多尺度特征（可选，针对小目标棋子）
  • 位置编码：为 DETR 头注入 2D 位置信息

3.2.2 棋盘角点检测头

关键角点检测是后续透视变换的前提，精度直接影响 FEN 正确性。

  • 设计：4 关键点回归（A0、A8、J0、J8 四个角）
  • 参考：YOLO-Pose 的角点检测思路，pose loss 权重可调高至 24.0
  • 输出：4 个 (x, y) 坐标 + 置信度

3.2.3 棋子检测头（DETR）

推荐用 DETR head 而非 YOLO head，因为 DETR 天然接受 ViT 的单尺度序列输出。

  • 输入：适配后的特征序列 + 位置编码
  • 输出：N 个 query，每个预测 (边界框, 类别, 置信度)
  • 类别：红/黑 × 车马象士将炮兵 = 14 类
  • 训练：匈牙利匹配 + 集合预测损失

3.2.4 透视变换与网格映射

角点检测结果 → 透视变换（拉直棋盘）→ 标准俯视图
                ↓
棋子边界框中心点 → 映射到 9×10 网格坐标
                ↓
              生成 FEN 字符串

⚡ 修订注：角点顺序/网格映射约定应与手机项目 BoardGeometry（TL,TR,BR,BL + MARGIN/CELL canonical 系）对齐，保证 v10 数据集跨项目通用。

3.3 决策引擎：Pikafish

不可替代：Pikafish 是确定性搜索引擎，棋力远超任何大模型。

输出项 说明 用途
最佳走法 如 炮二平五 推荐给用户、可视化箭头
评分 Centipawn，如 +35 判断优劣、渲染评分条
PV（主变） 后续若干步最佳应对 生成"如果…则…"的评论
搜索深度 如 depth=28 评估分析可信度

⚡ 修订注：Pikafish 为 GPL 协议——PC 工具链使用无碍；若未来服务化对外提供需复核协议。

3.4 语言分支

3.4.1 投影层

将 Vision Encoder 的视觉特征映射到语言塔的词嵌入空间。

  • 方案 A：MLP：2-3 层全连接，轻量，LLaVA 标准做法
  • 方案 B：Q-Former：可学习 query 压缩视觉 token，BLIP-2 做法
  • 方案 C：直接复用 Qwen-VL 自带投影：省去训练

3.4.2 语言塔（Qwen 2B / 4B）

核心：语言塔是系统的"嘴巴和教练"，负责把结构化信息翻译成自然语言。

输入组成：

输入来源 作用
FEN 检测分支告诉模型"局面是什么"
引擎走法 + 评分 + PV Pikafish 告诉模型"为什么这步好"
视觉 token 投影层告诉模型"现在是什么场景"
用户问题 ASR / 文本，告诉模型"用户想知道什么"

输出示例：

  • 局面讲解："红方中炮对屏风马，双方子力均衡"
  • 走法解释："炮二平五控制中路，给左翼马让路"
  • 评论教学："这步是稳健开局，如果你想搏杀可以试试炮八平五"
  • 交互回答："你上一步马八进七过早，导致右翼空虚"

3.5 可视化渲染层

参考 Qwen-Drive 的"显式探针"理念，所有中间结果都可视叠加：

可视化元素 数据来源 渲染方式
棋盘角点 角点检测头 四点连线框
棋子检测框 棋子检测头 边界框 + 类别标签
棋盘状态面板 FEN 侧边栏 9×10 网格图
推荐走法 Pikafish 箭头 + 高亮起止格
评分条 Pikafish 红黑方优势条
评论文字 Qwen 对话气泡 / 字幕

7. 与 Qwen-Drive 的对比

维度 Qwen-Drive 本系统
共享基座 Qwen3.5-4B VLM Vision Encoder（DINOv2/SigLIP）+ Qwen
外挂感知头 BEV 感知头（3D 检测 + 占用 + 分割） 角点头 + 棋子检测头（DETR）
外挂规划专家 扩散 Transformer 生成轨迹 Pikafish 搜索走法
耦合方式 紧耦合，外挂模块从 VLM 特征读取 紧耦合，检测头与语言塔共享 Encoder
显式探针 3D 框、地图分割可视化 角点、棋子框、FEN、走法箭头
规划方式 模型学习轨迹生成 引擎搜索 + 模型解释
核心差异 规划由模型完成 规划由引擎完成，模型只解释

为什么本系统不让模型做规划？

  • 象棋搜索空间 10^40+，语言 token 空间无法覆盖
  • 引擎每秒搜索数百万节点，模型无法匹敌
  • 走法最优性无快速验证器，模型无法自我纠正
  • 实时性要求毫秒级，模型推理延迟过高

模型负责"编排引擎 + 解释结果 + 生成评论"，这是它最擅长的能力区间。

8. 关键设计决策与权衡

8.1 为什么用 DETR head 而非 YOLO head？

维度 YOLO head DETR head
输入格式 需要多尺度特征金字塔 单尺度序列即可
与 ViT 匹配 需额外 Neck 适配 天然匹配
训练复杂度 需 Anchor 设计 匈牙利匹配，端到端
成熟案例 YOLO 生态 RF-DETR、DINO-DETR

结论：DETR head 与 ViT 输出格式天然匹配，是共享 Encoder 架构下的首选。

⚡ 修订注：RF-DETR 本身就是「DINOv2 底座 + DETR 头」的成熟开源实现（手机项目方案 A 的标注主力）。 阶段 1 的检测分支应直接以 RF-DETR 为起点（含 4 角点关键点扩展），而非从零自建适配层 + DETR 头—— 省掉 Hungarian 匹配/查询数/Neck 的一整套调参。本节结论不变，实现路径修正。

8.2 为什么冻结 Vision Encoder？

  • 梯度冲突风险：检测损失关注局部边缘，语言损失关注全局语义，同时反向传播会互相干扰。
  • 方案：先冻结 Encoder，只训检测头和投影层
  • 可选：阶段 4 用 LoRA 轻微适配，但需监控检测精度（⚡ 修订：阶段 4 已删）
  • 备选：如果 Qwen-VL 自带 ViT，可直接复用其已对齐的特征

8.3 为什么两路适配器分离？

分支 需要适配器
检测头 2D 空间结构、多尺度：reshape + Neck + 位置编码
语言塔 序列 token、语义嵌入：MLP / Q-Former 投影

两者需求不同，不能共用一路适配。

8.4 为什么语言塔必须接收 FEN + 引擎信息？

  • 没有 FEN：模型不知道当前局面，只能泛泛而谈。
  • 没有引擎信息：模型不知道这步棋为什么好，无法解释。
  • 只有视觉 token：模型看到画面但缺乏精确局面表示，容易"瞎说"。

三者缺一不可：FEN 给局面，引擎给分析，视觉 token 给场景上下文。

8.5 视觉 token 的真正价值

当 FEN 和引擎信息已经提供精确局面时，视觉 token 补充的是：

视觉提供 对评论的影响
棋盘朝向、红黑方视角 判断"谁在走"
棋子被手遮挡的模糊状态 判断"是否在摆棋"
对局阶段视觉线索 调整评论语气
用户手势、表情 判断用户意图
棋盘外环境（比赛/教学/直播） 调整解说风格

视觉不是替代 FEN，而是让评论"有场景感、有语气、有交互性"。

⚡ 修订注：正因如此，视觉 token（阶段 2）的投入应后置于 B0 验证（见 §5.1 修订）。

9. ⚡ 与手机项目方案 A 的关系（评审新增）

手机项目（chinese_chess_coach_phone_version）的方案 A：PC 强模型自动标注（RF-DETR）与本方案阶段 1 是同一件事的两个视角——检测能力 + 数据引擎必须共用，不能做两套：

方案 A（手机项目维护）= 数据引擎（RF-DETR 自动标注 → v10 数据集）+ 端侧蒸馏（YOLOv8n-pose）
本方案 阶段 1 = 直接消费 v10 数据集训练检测分支（以 RF-DETR 为起点做共享基座扩展）
  • v10 数据集是两个项目的公共资产（角点 GT 约定已对齐 BoardGeometry，见 §3.2.4 注）
  • A 的 M1' spike（RF-DETR 棋盘标注）先行——它同时是本方案检测分支的可行性验证
  • 本方案的独有增量只在语言分支（投影层 + Qwen 塔语料/训练）与渲染层

10. ⚡ 事实一致性自动闸（评审新增）

防幻觉从「原则」落为「可测指标」：LLM 输出中出现的每个着法、评分、局面断言，必须能对齐到引擎结构化输出：

  • 着法 ∈ {best_move} ∪ PV ∪ 合法着法表（经 Pikafish 校验）
  • 评分表述与 score 同号且量级一致（"略优/大优"分档）
  • 局面描述（子力、谁在走）与 FEN 解析结果一致

实现为一个独立校验器（规则即可，无需模型），用于：

  1. 训练语料自动过滤（GPT-4 生成的评论先过闸再入训练集）
  2. 推理时输出后校验，不通过的句子降级为模板兜底
  3. 讲解质量的自动评测指标（事实一致率）
