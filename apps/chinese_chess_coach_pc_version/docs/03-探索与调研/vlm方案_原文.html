1. 设计目标与核心思路

1.1 系统目标

基于真实象棋视频/图像，实现以下能力：

  • 视觉感知：从画面中识别棋盘角点与棋子位置
  • 局面重建：将检测结果映射为标准的 FEN 局面表示
  • 走子建议：调用 Pikafish 引擎计算最佳走法、评分与候选变化
  • 智能评论：结合局面、引擎分析、视觉场景，生成自然语言讲解与教学评论
  • 可视化渲染：将检测框、棋盘状态、推荐走法、评论文字叠加回原画面

1.2 核心设计思路

共享视觉基座：图像只经过一次 Vision Encoder，检测头与语言塔共享其视觉特征，避免重复计算，保证语义一致。
检测与语言双分支：检测头读取空间特征图做精确定位；语言塔读取投影后的视觉 token 做场景理解，两路适配器分离。
专用模块做专用事：检测头负责“找棋子”，Pikafish 负责“算走法”，Qwen 负责“说人话”，各司其职。
引擎不替代、模型不越界：不让 VLM 学下棋，而是让它编排引擎、解释结果、生成评论。
分阶段训练：检测头、投影层、语言塔 LoRA 依次训练，4060 显存可控。

1.3 系统边界

模块负责不负责
Vision Encoder提取通用视觉特征不做具体检测或语言生成
棋盘角点检测头定位 4 个棋盘角点不识别棋子
棋子检测头（DETR）输出棋子边界框 + 类别不生成 FEN、不下棋
PikafishFEN → 最佳走法 + 评分 + PV不生成自然语言
Qwen 语言塔局面讲解、走法解释、评论生成不做精细定位、不做搜索

3. 模块详解

3.1 共享视觉编码器

核心图像只经过一次编码，检测头和语言塔共享同一套视觉表征。

候选模型特点适用性
DINOv2 / DINOv3自监督预训练，冻结特征质量极高，擅长密集预测推荐角点、边缘敏感
SigLIP图文对齐预训练，语义理解强可选语言对齐友好
CLIP ViT生态成熟，社区资源多备选分辨率偏低
Qwen-VL 自带 ViT与 Qwen 语言塔天然对齐推荐省去投影层训练

输出格式：单尺度特征图 (B, N, D) 或 (B, D, H, W)，其中 N 为 patch 数量，D 为特征维度。

3.2 检测分支

3.2.1 检测适配层

Vision Encoder 输出的是单尺度序列特征，检测头需要 2D 空间结构或多尺度金字塔。适配层负责：

  • reshape：将 (B, N, D) 还原为 (B, D, H, W)
  • Neck：从中间层抽取多尺度特征（可选，针对小目标棋子）
  • 位置编码：为 DETR 头注入 2D 位置信息

3.2.2 棋盘角点检测头

关键角点检测是后续透视变换的前提，精度直接影响 FEN 正确性。

  • 设计：4 关键点回归（A0、A8、J0、J8 四个角）
  • 参考：YOLO-Pose 的角点检测思路，pose loss 权重可调高至 24.0
  • 输出：4 个 (x, y) 坐标 + 置信度

3.2.3 棋子检测头（DETR）

推荐用 DETR head 而非 YOLO head，因为 DETR 天然接受 ViT 的单尺度序列输出。

  • 输入：适配后的特征序列 + 位置编码
  • 输出：N 个 query，每个预测 (边界框, 类别, 置信度)
  • 类别：红/黑 × 车马象士将炮兵 = 14 类
  • 训练：匈牙利匹配 + 集合预测损失

3.2.4 透视变换与网格映射

角点检测结果 → 透视变换（拉直棋盘）→ 标准俯视图
                                      ↓
棋子边界框中心点 → 映射到 9×10 网格坐标
                                      ↓
                        生成 FEN 字符串

3.3 决策引擎：Pikafish

不可替代Pikafish 是确定性搜索引擎，棋力远超任何大模型。

输出项说明用途
最佳走法如 炮二平五推荐给用户、可视化箭头
评分Centipawn，如 +35判断优劣、渲染评分条
PV（主变）后续若干步最佳应对生成“如果…则…”的评论
搜索深度如 depth=28评估分析可信度

3.4 语言分支

3.4.1 投影层

将 Vision Encoder 的视觉特征映射到语言塔的词嵌入空间。

  • 方案A：MLP：2-3 层全连接，轻量，LLaVA 标准做法
  • 方案B：Q-Former：可学习 query 压缩视觉 token，BLIP-2 做法
  • 方案C：直接复用 Qwen-VL 自带投影：省去训练

3.4.2 语言塔（Qwen 2B / 4B）

核心语言塔是系统的“嘴巴和教练”，负责把结构化信息翻译成自然语言。

输入组成：

输入来源作用
FEN检测分支告诉模型“局面是什么”
引擎走法 + 评分 + PVPikafish告诉模型“为什么这步好”
视觉 token投影层告诉模型“现在是什么场景”
用户问题ASR / 文本告诉模型“用户想知道什么”

输出：

  • 局面讲解：“红方中炮对屏风马，双方子力均衡”
  • 走法解释：“炮二平五控制中路，给左翼马让路”
  • 评论教学：“这步是稳健开局，如果你想搏杀可以试试炮八平五”
  • 交互回答：“你上一步马八进七过早，导致右翼空虚”

3.5 可视化渲染层

参考 Qwen-Drive 的“显式探针”理念，所有中间结果都可视叠加：

可视化元素数据来源渲染方式
棋盘角点角点检测头四点连线框
棋子检测框棋子检测头边界框 + 类别标签
棋盘状态面板FEN侧边栏 9×10 网格图
推荐走法Pikafish箭头 + 高亮起止格
评分条Pikafish红黑方优势条
评论文字Qwen对话气泡 / 字幕

7. 与 Qwen-Drive 的对比

维度Qwen-Drive本系统
共享基座Qwen3.5-4B VLMVision Encoder（DINOv2/SigLIP）+ Qwen
外挂感知头BEV 感知头（3D 检测 + 占用 + 分割）角点头 + 棋子检测头（DETR）
外挂规划专家扩散 Transformer 生成轨迹Pikafish 搜索走法
耦合方式紧耦合，外挂模块从 VLM 特征读取紧耦合，检测头与语言塔共享 Encoder
显式探针3D 框、地图分割可视化角点、棋子框、FEN、走法箭头
规划方式模型学习轨迹生成引擎搜索 + 模型解释
核心差异规划由模型完成规划由引擎完成，模型只解释

为什么本系统不让模型做规划？

  • 象棋搜索空间 10^40+，语言 token 空间无法覆盖
  • 引擎每秒搜索数百万节点，模型无法匹敌
  • 走法最优性无快速验证器，模型无法自我纠正
  • 实时性要求毫秒级，模型推理延迟过高

模型负责“编排引擎 + 解释结果 + 生成评论”，这是它最擅长的能力区间。

8. 关键设计决策与权衡

8.1 为什么用 DETR head 而非 YOLO head？

维度YOLO headDETR head
输入格式需要多尺度特征金字塔单尺度序列即可
与 ViT 匹配需额外 Neck 适配天然匹配
训练复杂度需 Anchor 设计匈牙利匹配，端到端
成熟案例YOLO 生态RF-DETR、DINO-DETR

结论：DETR head 与 ViT 输出格式天然匹配，是共享 Encoder 架构下的首选。

8.2 为什么冻结 Vision Encoder？

梯度冲突风险：检测损失关注局部边缘，语言损失关注全局语义，同时反向传播会互相干扰。

  • 方案：先冻结 Encoder，只训检测头和投影层
  • 可选：阶段 4 用 LoRA 轻微适配，但需监控检测精度
  • 备选：如果 Qwen-VL 自带 ViT，可直接复用其已对齐的特征

8.3 为什么两路适配器分离？

分支需要适配器
检测头2D 空间结构、多尺度reshape + Neck + 位置编码
语言塔序列 token、语义嵌入MLP / Q-Former 投影

两者需求不同，不能共用一路适配。

8.4 为什么语言塔必须接收 FEN + 引擎信息？

没有 FEN：模型不知道当前局面，只能泛泛而谈。

没有引擎信息：模型不知道这步棋为什么好，无法解释。

只有视觉 token：模型看到画面但缺乏精确局面表示，容易“瞎说”。

三者缺一不可：FEN 给局面，引擎给分析，视觉 token 给场景上下文。

8.5 视觉 token 的真正价值

当 FEN 和引擎信息已经提供精确局面时，视觉 token 补充的是：

视觉提供对评论的影响
棋盘朝向、红黑方视角判断“谁在走”
棋子被手遮挡的模糊状态判断“是否在摆棋”
对局阶段视觉线索调整评论语气
用户手势、表情判断用户意图
棋盘外环境（比赛/教学/直播）调整解说风格

视觉不是替代 FEN，而是让评论“有场景感、有语气、有交互性”。
