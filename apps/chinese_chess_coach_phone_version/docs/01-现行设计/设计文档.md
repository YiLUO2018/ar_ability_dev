## 1. 项目概述

### 1.1 项目背景
本项目是「中国象棋教练」应用的核心功能验证版，完全基于 Android 手机实现，不依赖 AR 眼镜硬件。通过手机摄像头实时采集棋盘画面，在手机端完成「视频流采集 → 棋面识别 → 局面构建 → 走子建议 → 结果显示」的完整闭环，为后续眼镜端方案验证核心逻辑、算法与数据流。

### 1.2 设计初衷
- 利用 Android 手机的成熟摄像头、算力与显示能力，快速验证核心功能。
- 不依赖 AR 眼镜及 Rokid SDK，降低开发与调试门槛。
- 与 `chinese_chess_coach`（眼镜版）共享棋面识别与走子引擎逻辑，便于后续迁移。
- 先在手机端跑通完整闭环，再平滑移植到眼镜端。

### 1.3 与眼镜版的关系
| 维度 | chinese_chess_coach（眼镜版） | 本应用（手机版） |
| :--- | :--- | :--- |
| 采集端 | Rokid Glasses 摄像头 | Android 手机摄像头 |
| 算力端 | 手机（外置算力） | 手机（本地算力） |
| 显示端 | 眼镜镜片（绿色 UI） | 手机屏幕 |
| 传输 | BLE 传输图片 | 无需跨设备传输 |
| 目的 | 最终产品形态 | 核心功能验证 |

### 1.4 核心需求
| 需求项 | 说明 |
| :--- | :--- |
| **视频流采集** | 通过 Android 手机摄像头实时采集棋盘画面 |
| **棋盘定位** | 检测画面中的棋盘，透视校正为规整的 9×10 网格 |
| **棋子识别** | 识别每个交叉点的棋子类别（红黑 + 7 种棋子） |
| **局面构建** | 将识别结果映射为内部局面表示（如 FEN） |
| **走子建议** | 调用象棋引擎计算下一步最佳走法 |
| **结果显示** | 在手机屏幕上叠加显示建议走法（高亮起始/目标点、箭头） |
| **可验证性** | 作为眼镜版核心功能的验证平台 |

## 2. 系统架构

### 2.1 总体架构

```
┌───────────────────────────────────────────────┐
│              Android 手机 App                  │
│  ┌─────────────────────────────────────────┐  │
│  │  CameraX / Camera2  视频流采集           │  │
│  └─────────────────────────────────────────┘  │
│                    ↓ 视频帧                    │
│  ┌─────────────────────────────────────────┐  │
│  │  棋盘定位模块（OpenCV 直线/角点→透视变换）│  │
│  └─────────────────────────────────────────┘  │
│                    ↓ 规整棋盘图                │
│  ┌─────────────────────────────────────────┐  │
│  │  棋子识别模块（深度学习分类每个交叉点）   │  │
│  └─────────────────────────────────────────┘  │
│                    ↓ 棋子位置/类别             │
│  ┌─────────────────────────────────────────┐  │
│  │  局面构建模块（映射为 FEN/内部表示）      │  │
│  └─────────────────────────────────────────┘  │
│                    ↓ 局面                     │
│  ┌─────────────────────────────────────────┐  │
│  │  走子引擎模块（XQWLight，JNI 调用）      │  │
│  └─────────────────────────────────────────┘  │
│                    ↓ 最佳走法                  │
│  ┌─────────────────────────────────────────┐  │
│  │  叠加渲染（高亮走法 + 坐标映射）          │  │
│  └─────────────────────────────────────────┘  │
└───────────────────────────────────────────────┘
```

### 2.2 数据流

```
1. 手机摄像头采集视频帧
2. 棋盘定位模块检测棋盘角点/网格线，透视校正为规整棋盘图
3. 棋子识别模块对 90 个交叉点逐点分类（空 / 14 种棋子）
4. 局面构建模块将分类结果映射为内部局面表示（FEN）
5. 走子引擎模块输入局面，计算最佳走法
6. 在屏幕上叠加渲染建议走法（起始点/目标点高亮 + 箭头）
7. 循环执行 1-6，形成实时教练
```

## 3. 技术选型

### 3.1 摄像头采集
| 方案 | 优点 | 缺点 | 选择 |
| :--- | :--- | :--- | :--- |
| **CameraX** | 官方推荐、生命周期感知、易用 | 对底层控制较弱 | **首选** |
| Camera2 | 控制精细、性能好 | 使用复杂 | 备选 |

### 3.2 棋面识别方案（核心约束：运行时零 Google Play 依赖）
> 国内手机普遍无 Google Play（GMS），因此**必须离线本地推理**：模型打包进 APK，运行时零 GMS 依赖。

采用**混合方案**：OpenCV 负责棋盘定位与透视校正，深度学习负责棋子分类。

| 子环节 | 方案 | 说明 |
| :--- | :--- | :--- |
| 棋盘定位 | **OpenCV**（Canny 边缘 + Hough 直线 + 角点检测） | 检测棋盘外框/网格线，计算四角，透视变换到规整 9×10 网格 |
| 棋子定位 | 固定网格交叉点 | 透视校正后棋子落在 90 个交叉点上，无需单独检测框 |
| 棋子分类 | **TFLite 分类模型** | 对每个交叉点 ROI 分类：空 + 红/黑 × 7 类 = 15 类 |
| 备选分类 | OpenCV 颜色阈值 + 模板匹配 | 无模型时的降级方案，识别红黑 + 少量字形 |

> 说明：中国象棋棋子是落在交叉点上的圆饼，字形固定（帅/将、仕/士、相/象、马、车、炮、兵/卒，红黑共 14 种字形 + 空位）。透视校正后按固定网格逐交叉点切 ROI 分类，是比通用目标检测更稳、更轻的方案。

### 3.3 走子建议引擎
| 方案 | 优点 | 缺点 | 选择 |
| :--- | :--- | :--- | :--- |
| **XQWLight（象棋小巫师）** | 开源、轻量、真实棋力、支持 UCCI 协议 | 需 NDK/JNI 集成 C++ 代码 | **首选** |
| 纯 Kotlin 规则引擎 | 无 NDK、集成简单 | 棋力弱 | 占位/降级 |
| 云端引擎 | 棋力强 | 需网络与后端，国内部署成本高 | 备选 |

> XQWLight 集成方式：通过 NDK 编译为 `libxqwlight.so`，JNI 封装为 `ChessEngine` 接口；引擎按 UCCI 协议输入局面（FEN）、输出 `bestmove`。后续换引擎（如 ElephantEye / Pikafish 象棋子版本）只加实现、改工厂一行。

### 3.4 开发环境
- **IDE**：Android Studio
- **语言**：Kotlin（业务）+ C/C++（引擎，NDK）
- **minSdk**：24 (Android 7+)
- **compileSdk / targetSdk**：37（本机 SDK）
- **核心依赖**：CameraX 1.6.0、OpenCV 4.x、TFLite 2.16.x、NDK

### 3.5 模块可替换架构（接口隔离）

```
UI 层（MainActivity + OverlayView）
        │ 只依赖接口
引擎层：BoardDetector / PieceRecognizer / ChessEngine 接口 + ChessEngine 工厂
        ├── OpenCV 棋盘定位实现
        ├── TFLite 棋子识别实现（后续可换模型/OpenCV 模板）
        └── XQWLight 走子引擎实现（JNI；后续可换引擎）
数据层：局面表示（FEN）+ 走法生成/合法性校验
```

- 定义与实现无关的 `BoardInfo`（棋盘四角/网格）、`Piece`（红黑 + 类型）、`Move`（起点/终点）数据类。
- `ChessEngine` 工厂按配置返回具体实现，换模型/引擎只改工厂，不动调用方。
- 模型文件统一放 `assets/models/`，引擎 native 库放 `jniLibs/`，随 APK 打包、运行时本地加载。

## 4. 详细工作流

### 4.1 第一阶段：环境搭建
1. 新建 Android 项目，集成 CameraX。
2. 配置 NDK，接入 OpenCV 与 TFLite 依赖。
3. 实现摄像头预览与视频帧回调。

### 4.2 第二阶段：棋盘定位
```kotlin
// 示例：视频帧回调中定位棋盘
override fun analyze(imageProxy: ImageProxy) {
    val bitmap = imageProxy.toBitmap()
    val board = boardDetector.detect(bitmap)  // 输出棋盘四角/网格坐标，或 null
    if (board != null) {
        val warped = boardDetector.warp(bitmap, board)  // 透视校正到规整棋盘
        // 交给棋子识别
    }
    imageProxy.close()
}
```

### 4.3 第三阶段：棋子识别
```kotlin
// 示例：对规整棋盘逐交叉点分类
val pieces = pieceRecognizer.recognize(warped)  // 返回 9×10 网格，每点空/棋子
val position = positionBuilder.build(pieces)    // 生成内部局面表示
```

### 4.4 第四阶段：走子建议
```kotlin
// 示例：调用引擎计算最佳走法
val move = chessEngine.bestMove(position)  // 返回最佳走法，如 "炮二平五"
```

### 4.5 第五阶段：叠加显示
- 在预览层上叠加自定义 View，将走法坐标映射回画面。
- 高亮起始点与目标点，绘制方向箭头。

### 4.6 第六阶段：优化与验证
- 控制识别频率，避免过高 CPU 占用。
- 对比不同模型的延迟与准确率。
- 验证识别与走法正确性，为眼镜版迁移做准备。

## 5. 关键实现细节

### 5.1 棋盘模型与坐标
- 棋盘为 **9 列 × 10 行** 交叉点，共 **90** 个落子点（棋子落于交叉点，非格内）。
- 中间「楚河汉界」将棋盘分为上下两半（红方在下、黑方在上）。
- 坐标表示：`(file, rank)`，file ∈ [0,8]，rank ∈ [0,9]；支持中国象棋记谱（如「炮二平五」）。

### 5.2 棋子类别（共 14 种字形 + 空位）
| 方 | 帅/将 | 仕/士 | 相/象 | 马 | 车 | 炮 | 兵/卒 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 红方 | 帅 | 仕 | 相 | 马 | 车 | 炮 | 兵 |
| 黑方 | 将 | 士 | 象 | 马 | 车 | 炮 | 卒 |

> 棋子分类为 15 类问题：空 + 14 种棋子（红黑共 7 组字形，其中 马/车/炮 红黑同字）。

### 5.2.1 TFLite 分类模型契约（已实现）
代码已按此契约实现 `TFLitePieceRecognizer`；模型文件放置后即生效，否则由工厂自动降级为模板匹配。

| 项 | 约定 |
| :--- | :--- |
| 模型路径 | `assets/models/piece_classifier.tflite` |
| 输入 | float32 `[1, H, W, 3]`，RGB，取值 `[0,1]`，H/W 从输入张量形状读取（约定正方形） |
| 输出 | float32 `[1, 15]`，取 argmax 作为类别 |
| 类别映射 | 0 = 空位；1–7 = 红方 帅/仕/相/马/车/炮/兵；8–14 = 黑方 将/士/象/马/车/炮/卒 |

> 类别顺序与 `PieceType.entries`（GENERAL→PAWN）一致：`(label-1) % 7` 得棋种，`label <= 7` 判红方。

### 5.3 性能指标
| 环节 | 目标 |
| :--- | :--- |
| 视频帧采集 | 15-30 fps |
| 棋盘定位延迟 | < 50ms |
| 棋子识别延迟 | < 50ms |
| 走子建议延迟 | < 1s（引擎搜索时间） |
| 完整闭环延迟 | < 1.5s |
| 内存占用 | 复用 Bitmap，避免 OOM |

### 5.4 内存管理
- 视频帧及时回收，使用 `inBitmap` 复用。
- 识别结果按帧更新，不累积历史数据。
- 引擎搜索在独立线程执行，避免阻塞 UI 与相机回调。

## 6. 与眼镜版的差异

| 项目 | 手机版 | 眼镜版 |
| :--- | :--- | :--- |
| 视频流来源 | 手机摄像头 | 眼镜摄像头（BLE 传输） |

| 通信 | 本地直接处理 | 跨设备 BLE 传输 |
| 核心逻辑（识别、引擎、走法） | 一致 | 一致 |

## 7. 待解决问题

1. **棋盘定位鲁棒性**：不同光照、角度、部分遮挡下的棋盘角点检测准确性需验证。
2. **棋子分类模型**：需准备/训练 15 类棋子分类模型（红黑 14 字形 + 空位），模型来源与精度待定。
3. **XQWLight 集成**：NDK 编译、JNI 封装、UCCI 协议对接的具体实现待验证。
4. **识别与引擎一致性**：识别结果构建的局面与真实棋盘是否一致，需走法校验。
5. **实时性**：OpenCV + 模型 + 引擎在手机端同时运行时的延迟需测试。
6. **模型文件国内下载**：TFLite 模型若托管于 Google storage，国内下载需代理/镜像。
