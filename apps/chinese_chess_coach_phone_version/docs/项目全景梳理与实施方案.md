## 0. 一句话现状

> **棋盘定位（SAM/EdgeSAM 分割）已经稳定跑通（~3–4px），但棋子识别（合成数据训练的整盘分类器）在真实照片上失效，导致「下一步走法建议」整条链路在最后一步断掉。**

**进度（2026-10-06）**：数据生成侧（M0–M5）与训练（M6）已全部跑通，进入 **M7 端侧闭环**：

- M0–M4 全部完成（SAM 逐子分割 → 交点/占位 → 开局识别 → 视频 from→to + 身份传播，25 步规则自洽）。

- **跨场景泛化**：在非训练视频的真实照片 `board_21` 上检出 **29/38** 子，黑方全齐、**红方漏红马/红炮**——单视频训练仍有域差，用数据飞轮（端侧采集 → 自动标注 → 重训）迭代收敛。

详见 §6.4。

## 1. 项目概述

### 1.1 目标

用 Android 手机摄像头**实时**对准一张真实的中国象棋棋盘，完成：

```
相机视频流 → 棋盘定位 → 透视校正 → 棋子识别 → 局面构建 → 引擎算下一步 → 屏幕叠加显示走法建议
```

这是「中国象棋教练」眼镜版（Rokid）的**手机端验证平台**：先在手机端跑通核心逻辑，再移植到眼镜端。核心约束：**运行时零 Google Play（GMS）依赖**，所有模型/引擎本地离线运行。

### 1.2 核心需求

| 需求 | 说明 |
| :-- | :-- |
| 视频采集 | CameraX 实时采集棋盘画面 |
| 棋盘定位 | 检测画面中棋盘，透视校正为规整 9×10 网格 |
| 棋子识别 | 识别 90 个交叉点上每颗棋子的「红黑 + 7 种棋子」 |
| 局面构建 | 识别结果映射为内部局面表示（FEN） |
| 走子建议 | 引擎计算当前局面最佳走法 |
| 结果显示 | 屏幕叠加高亮起点/终点 + 箭头 |

## 2. 端到端数据流与各阶段理论

```
┌──────────────────────────────────────────────────────────────┐
│ ① CameraX 视频采集                                            │
│     ↓  每帧 Bitmap                                            │
│ ② BoardDetector 棋盘定位                                       │
│     输出：棋盘物理四角 corners（8 个 float）                    │
│     ↓  四角 → 单应矩阵 H                                       │
│ ③ 透视校正 warp → canonical 规整棋盘图（450×500）               │
│     ↓  warped 位图                                            │
│ ④ PieceRecognizer 棋子识别                                     │
│     输出：9×10 网格 Array<Array<Piece?>>                        │
│     ↓                                                         │
│ ⑤ Board 局面构建（FEN / 内部表示）                              │
│     ↓                                                         │
│ ⑥ ChessEngine 走子建议                                        │
│     输出：Move(from, to)                                       │
│     ↓                                                         │
│ ⑦ BoardOverlayView 叠加渲染（grid→image 映射画箭头）            │
└──────────────────────────────────────────────────────────────┘
```

### 2.1 各阶段职责与「为什么这样拆」

- **② 定位回答「棋盘在哪」**：输出 4 个明确角点，是后续单应映射（透视校正 + UI 叠加）的几何基础。
- **④ 识别回答「每格是什么」**：在 warped 规整棋盘上分类，尺度归一化、位置确定（棋子必落交叉点），无需目标检测框。
- **定位与识别分离**：两者独立训练、独立替换、独立验证，互不耦合。

## 3. 模块详细理论

### 3.1 视频采集（CameraX）

- CameraX 1.6.0，`ImageAnalysis` 帧回调，`STRATEGY_KEEP_ONLY_LATEST` 丢帧策略。
- YUV(NV21) → JPEG → Bitmap，按旋转角 `rotationDegrees` 校正，前置摄像头额外镜像。
- 关键参数：`DETECT_EVERY_N = 5`（每 5 帧检测一次，控制算力）。

### 3.2 棋盘定位（BoardDetector）

#### 为什么必须输出「四个角点」而不是「轴对齐框」？

UI 叠加要把「棋盘网格坐标 (file, rank)」映射回「画面像素坐标」。斜拍下棋盘是透视梯形，只有 4 个角点 + 单应矩阵能精确描述这个透视映射；轴对齐框做不到。

#### 三种实现及结局

| 实现 | 原理 | 结局 |
| :-- | :-- | :-- |
| `GridBoardDetector` | OpenCV 式：Sobel 边缘 + Hough 直线 + 角度分族 + 极值求角 | ✗ 失效：斜拍竖线偏离竖直 7–17°，超出固定角度带，竖线漏检，误差 ~110px |
| `KeypointBoardDetector` | 轻量 CNN + 热力图 + DSNT 软 argmax 回归四角（**合成数据训练**） | ✗ 失效：合成→真实域差，输出垃圾角点但置信度 ~1.0，门控失效 |
| `SegmentationBoardDetector` | **EdgeSAM 分割**：图像编码 → 点提示 → 掩码 → 拟合四角 | ✅ **稳定（~3–4px）** |

#### 方向 A 核心：EdgeSAM 端上分割（当前主路径）

- EdgeSAM 官方无 TFLite，改用 **ONNX Runtime**（`onnxruntime-android 1.22.0`）跑两个 ONNX：
  - `edge_sam_3x_encoder.onnx`（22MB）：输入 `image` `[1,3,1024,1024]` NCHW float → 输出 `image_embeddings` `[1,256,64,64]`。
  - `edge_sam_3x_decoder.onnx`（16MB）：输入 `image_embeddings` + `point_coords` `[1,N,2]` + `point_labels` `[1,N]` → 输出 `scores` `[1,4]` + `masks` `[1,4,256,256]`（logits，阈值 0）。
- 预处理（与 EdgeSAM 官方 `Sam.preprocess` 对齐）：resize 长边→1024 → 每通道 `(v-mean)/std`（RGB mean=[123.675,116.28,103.53]，std=[58.395,57.12,57.375]）→ 右下补零到 1024²。
- 点提示坐标在 1024 帧坐标系（padding 在右下，无偏移）。
- 后处理：4 个候选掩码 → **按最大连通域面积选**（不是按分数，因为小块棋子/背景分数也能给到 1.0）→ 二值化 → 最大连通域 → 凸包 → 贪心减点到 4 顶点 → 排序 TL,TR,BR,BL。

#### 为什么 SAM/EdgeSAM 有效（理论）

SAM 是 SA-1B（1100 万图）预训练的零样本分割模型，对「桌面上的平面棋盘」这类前景/背景分离很擅长，不依赖棋盘纹理/光照/角度的先验，因此避开了合成数据训练的域差问题。

### 3.3 透视校正与单应矩阵（Homography）

#### 数学原理

4 组点对应确定一个单应矩阵 H（3×3，8 自由度，`h33=1`），用 DLT（直接线性变换）+ 高斯消元求解。单应描述「一个平面到另一平面的透视映射」。

#### canonical 几何（单一事实来源）

```
CELL = 50          # 相邻交叉点间距（像素）
MARGIN = 25        # 棋盘物理边到最外层网格线的距离
BOARD_W = 450      # = 25*2 + 50*8
BOARD_H = 500      # = 25*2 + 50*9
```

- 网格 **9 列（file 0..8）× 10 行（rank 0..9）**，共 **90 个交点**，棋子落在交叉点上。
- 交点 `(file, rank)` 在 canonical 图中位于 `(MARGIN + file*CELL, MARGIN + rank*CELL)`。
- rank 0 = 黑方底线（顶部），rank 9 = 红方底线（底部）。

#### ⚠️ 关键坑 1：物理棋盘边 vs 网格线交点（差 MARGIN=25px）

`BoardInfo.corners` 的语义**因检测器而异**：

| 检测器 | corners 语义 | warp 目标 |
| :-- | :-- | :-- |
| `SegmentationBoardDetector`（主路径） | **物理棋盘边四角** | `physicalCorners = (0,0),(450,0),(450,500),(0,500)` |
| `KeypointBoardDetector` / `GridBoardDetector`（降级） | **网格最外层交点** | `corners = (25,25),(425,25),(425,475),(25,475)` |

这两者差 25px（MARGIN），若混用会导致所有网格交点整体错位约半格。**这是历史上反复出现的坑**（`refine_corners` 的 33px 内缩误差、overlay 映射错位都源于此）。

#### ⚠️ 关键坑 2：warp 矩阵方向（Python 验证时必须对齐，2026-10-04 实测确认）

`cv2.warpPerspective` 与 Kotlin `Homography.warp` 的矩阵方向约定**相反**：

| 实现 | 传入矩阵语义 | 内部行为 |
| :-- | :-- | :-- |
| Kotlin `Homography.warp(src, ..., H)` | H 是 **dst→src**（对每个 dst 采样 src 在 H·dst） | 直接用 H 采样 |
| Python `cv2.warpPerspective(img, M)` | M 是 **src→dst**（forward） | 内部用 M⁻¹ 逆采样 |

**结论**：把 Kotlin 逻辑移植到 Python 验证时，矩阵要取反：

```python
# Kotlin: H_forward = compute(physicalCorners, corners)   # canonical→image
#          warp(pixels, ..., H_forward)                    # dst(canonical) 采样 src(image) 在 H_forward·dst

# Python 等价写法（方向相反）：
M = cv2.getPerspectiveTransform(corners_image, physicalCorners_canonical)  # image→canonical
warped = cv2.warpPerspective(img, M, (BOARD_W, BOARD_H))
```

> 我在 2026-10-04 写逐格裁剪原型时，先写成 `getPerspectiveTransform(PC, GT)`（方向反），导致 warp 结果棋盘挤在画面中心、四周黑边；改为 `getPerspectiveTransform(GT, PC)` 后棋盘正对填满整幅。此坑已用最小实验 + 真实帧验证确认。

### 3.4 棋子识别（PieceRecognizer）

#### 问题定义

15 类分类：**0 = 空位；1–7 = 红方 帅/仕/相/马/车/炮/兵；8–14 = 黑方 将/士/象/马/车/炮/卒**。

`PieceType` 顺序（GENERAL→PAWN）与 `fenChar`：

| 棋种 | FEN | 红名 | 黑名 |
| :-- | :-- | :-- | :-- |
| 帅/将 | k | 帅 | 将 |
| 仕/士 | a | 仕 | 士 |
| 相/象 | b | 相 | 象 |
| 马 | n | 马 | 马 |
| 车 | r | 车 | 车 |
| 炮 | c | 炮 | 炮 |
| 兵/卒 | p | 兵 | 卒 |

FEN 记谱：**小写 = 黑方，大写 = 红方**（马/车/炮红黑同字，靠大小写 + 颜色区分）。

#### 现有实现及结局

| 实现 | 原理 | 结局 |
| :-- | :-- | :-- |
| `TFLitePieceRecognizer` | 整盘分类：warped(450×500) 缩放 0.8× → `piece_classifier.tflite` `[1,400,360,3]→[1,15,10,9]`，一次出 90 格 | ✗ **失效（合成数据域差）** |
| `TemplatePieceRecognizer` | 交叉点占用检测 + HSV 判色 + 字形模板匹配 | △ 占位，准确率低 |

#### 失效根因（关键）

`piece_classifier.tflite` 用**合成数据**（`tools/data_gen/render.py` 程序化渲染）训练，验证集 99.99%，但真实照片上输出垃圾：

```
grid=..kkrkkk./...    （随机散落）
grid=.........        （全空）
```

与角点模型同病：**合成→真实域差**。合成渲染的棋子（规整字形、干净背景）与真实照片（斜拍、光照、反光、真实棋子材质）差距过大，模型学到错误先验。

#### 修复方向（已定，详见 §6.1）

最终选 **逐子检测（YOLO-nano，14 类）**：逐子独立、不假设棋子压交点（走子时棋子被拿起 / 在途也鲁棒）。训练数据用自动标注（方法 D）从真实视频生成，不依赖合成数据、不用现成权重。

### 3.5 局面构建（Board）

- 内部表示：`grid[rank][file]`，`Array(10) { arrayOfNulls(9) }`。
- 数据类：`Piece(color, type)`、`Move(fromFile, fromRank, toFile, toRank, piece, captured)`。
- FEN 导入/导出（`toFen` / `fromFen`），标准开局 FEN：
  `rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR w`
- 完整走法生成 + 合法性校验（`generateMoves` 过滤被将军/将帅照面），单测覆盖。

### 3.6 走子引擎（ChessEngine）

#### 当前实现：`KotlinChessEngine`（纯 Kotlin）

- **negamax + alpha-beta 剪枝**，深度 `DEFAULT_DEPTH = 3`（半回合）。
- 评估函数：**纯子力**（无位置分）：
  ```
  帅/将 100000；车 1000；炮 500；马 450；相 200；仕 200；兵 100（过河 200）
  ```
- 走法排序：吃子价值高者优先（提升剪枝效率）。
- 局限：无置换表、无静态搜索（quiescence）、无历史启发，棋力与走法质量有限。**但足以先跑通闭环。**

#### 后续增强（§6.2）

- **XQWLight（Java 移植版，GPL-2.0，2026-10-06 已落地）**：接成熟引擎（同 C++ 版算法/棋力，UCCI 协议），替代 Kotlin 自研引擎。免 NDK/JNI，`Position.java`/`Search.java`/`Util.java` 直入 `xqwlight` 包 + `XQWLightChessEngine` 桥接。
- 记谱（§6.5.2）：`Move` → 标准记谱「炮二平五」/「炮8进1」。

### 3.7 叠加显示（BoardOverlayView）

- 画黄色棋盘外框（4 角连线，反馈定位结果）。
- 画绿色箭头 + 起点/终点圆（走法建议）。
- **grid→image 映射用单应矩阵**（`Homography.transform`，透视精确），不再是早期错误的四角双线性插值。
- `toView`：源图坐标 → 视图坐标（PreviewView FILL_CENTER 缩放 + 居中裁剪）。

## 5. 核心问题与根因

### 5.1 合成→真实域差（两个模型都栽在这）

- 角点模型：合成渲染 → 真实斜拍，输出垃圾角点但置信度 1.0。
- 棋子分类器：合成渲染 → 真实照片，输出垃圾局面。

**根因**：`tools/data_gen/render.py` 的领域随机化不够，无法覆盖真实照片的分布（真实棋子材质/反光/阴影/斜拍透视/杂乱背景）。

### 5.2 坐标定义不统一（物理边 vs 网格交点）

差 MARGIN=25px，历史上导致多处错位（§3.3 关键坑 1）。

### 5.3 warp 矩阵方向约定不一致（Python vs Kotlin）

§3.3 关键坑 2，Python 验证时必须注意。

## 6. 重新确定的实施方案（按优先级）

### 6.1 【P0·阻塞项】修棋子识别（方案已定：自动标注 + YOLO 逐子检测，2026-10-05）

**最终决策**：端上改用 **YOLO-nano 逐子检测（14 类 = 7 红 + 7 黑）**；训练数据来自**自动标注**（方法 D：运动功能监督 + 标准开局引导），不再依赖合成数据。

**为什么不选另外两条路**：
- **整盘分类**（Swin / 现有 TFLite）：full-correct 仅 0.83，且 FCN 跨格串扰 + 合成域差，已弃。
- **逐格裁剪分类**：假设棋子必压交点，但真实对局走子时棋子被拿起 / 在途，裁剪会偏；检测逐子独立、不假设网格对齐，更鲁棒。

**训练数据怎么来（方法 D，完整细节见 `真实数据自动标注方案.md`）**：
1. **逐子定位**：SAM 在 90 交点逐点提示 → 棋子 mask → **bbox**（这就是检测器的 ground truth）。**必须在数据生成侧做到 38/38 全覆盖**（含偏移子，用邻域探针补漏），不能把偏移子留给 YOLO——YOLO 是端侧部署，会继承标注缺口。
2. **标准开局引导**：占位匹配识别开局 → 32 子身份免费到手 → 规则 forward 传播。
3. **运动推断身份**：运动分 7 类走法 + 外观 HSV 分红黑（运动色盲，红黑必须靠外观）。
4. **校验 + 重同步**：每步走法校验（未知子定身份 / 已知子验合法性）；断链后约束消解重建。

**可补充数据**：公开数据集（`Chinese_Chess808` 14类 724张 等）可作自动标注数据的补充，但**不是主来源**——合成/他人数据仍有域差，真实自拍视频才是主源。

**关键洞察**：认字是闭集单字识别（11 个字），加上「结构先验当监督」（象棋规则当 teacher），可以自动标注真实视频，绕开「合成→真实」域差——方法论沉淀见 `通用方法论-弱监督与数据标注.md`。

**训练结果（2026-10-06，M6 完成）**：yolov8n 在 `debug_video_01.mp4` 自动标注数据（184 图 / 5636 框 / 14 类）上训练，val mAP50=0.971、mAP50-95=0.907。关键教训：
- **扩量（每段多采 5 帧）不解决泛化**：val mAP 冲到 0.988 是训练/验证泄漏（同段相邻帧被随机拆进 train+val）。
- **根因是标签不完整，不是数据量**：SAM `detect_pieces` 漏检低对比黑方后线子（将/士/象/马 + 黑炮），YOLO 继承缺口 → 用 `m5_fill_gaps.py` 给「身份已知但 SAM 未检出」的格子补固定框（0.9 格）修好。
- **跨场景泛化仍不足**：board_21（另一套棋子）上漏红马/红炮 → 靠数据飞轮（§6.5）迭代。

**M1（交点检测 + 占位）——执行结果（2026-10-05 已完成 ✅）**：

棋盘四角是「棋盘定位」阶段的输出（端上 `SegmentationBoardDetector`，SAM 分割 → 拟合物理四角），M1 把它当**输入**，聚焦增量：单应 H + MARGIN → 90 交点；warp 投影找线校验 MARGIN。

*产出*：`tools/label_real/m1_intersections.py`（纯几何、无需 SAM，秒级）。

*结果*：
- **交点检测**：`H = getPerspectiveTransform(corners_image, PHYSICAL_CORNERS)` → 90 交点 = `(MARGIN+f*CELL, MARGIN+r*CELL)` 反投影回原图。M0 已验证此路径对齐正确（35 子质心距交点 < 14px）。

- **占位**：复用 M0 的 `predict_and_classify`（35/38 子，3 个偏移漏检）。

*发现（记录）*：SAM「画面中心点提示」对离中心偏移的棋盘（board_21 棋盘中心 (236,189) vs 图中心 (320,240)）会分割到背景/桌面；端上靠「质心回灌」解决（已实现），离线标注管线同理用上一帧质心跟踪。

**M5 的 bbox 标注组件（静态图逐子检测）——执行结果（2026-10-05 已完成 ✅）**：

*产出*：`tools/label_real/sam_detect_pieces.py`（SAM 逐子鲁棒检测，输出逐子 bbox + 可视化）。

*问题*：M0 的「交点单点提示」对偏离交点 ~0.5 格的棋子漏检（提示点落在空棋盘 → SAM 返回整块棋盘 mask）。数据生成侧必须把每颗子都标出 bbox，否则训练数据缺漏、YOLO 继承缺口。

*干净解法*（不引入全局质心聚类的桥接/合并坑）：
1. **基线** = M0 中心点提示（90 交点，面积比+圆度+质心距三重判，35/38、0 误报）；
2. **补漏** = 对「判空」的交点向 8 邻域（0.5 格）探针，收集偏移子候选；
3. **防重** = 邻域探针找到的 mask 与已认领 mask 高 IoU（>0.3）则丢弃（**找到后立即加入 claimed**，否则同一颗偏移子会被相邻多个空交点重复发现→多出假子）；
4. **分配** = 每个候选按「离它最近的仍空交点」一对一分配（而非第一个扫到的空交点）。

*结果*：**38/38 子检出、0 误报、bbox 干净**（~20–27px，无桥接大块）。3 个偏移子（file7/rank2 炮、file0/rank5、file7/rank6）全部补回。

*踩坑（记录）*：
- **桥接掩码**：SAM 单点提示在相邻棋子密集处（rank8/rank9 底线）会返回「桥接」掩码（两颗子连成 100×70 大块）。分类只认最大连通域（正确），但 bbox 若直接用全掩码就会变成大块——必须用 `largest_component_mask` 抠出单颗。
- **偏移子归属歧义**：单张静态图上，偏移 ~0.5 格的棋子其 (file, rank) 只能按「最近交点」给近似，可能偏到相邻交点（本次 file0/rank5→(0,6)、file7/rank6→(8,6)）。这类歧义由方法 D 的视频规则传播（M3/M4）消解，**不阻塞 M5 的 bbox 标注**。

*产出*：`debug_frames/board_21_sam_detect.png`（可视化）、`debug_frames/m5_bboxes.csv`（file,rank,x,y,w,h，原图像素坐标）。

#### 6.5.1 数据飞轮具体形式（最小闭环）

1. **采集触发**：YOLO 某子 conf < 阈值 / 局面非法（双帅、子数不对、子位置不合法）/ 定位失败 → 落盘 1 张 JPEG + 一行元数据（`BoardInfo` 四角 + YOLO 原始 bbox/class/conf）到 `filesDir/flywheel/`。
2. **导出**：app 加「导出采集帧」按钮打包 zip 分享/存相册；或 adb pull。
3. **离线标注**：复用现有 SAM 占位 + 标准开局匹配 + 规则校验管线（M0–M5），对「高置信 YOLO 框 + SAM 锚点」取并集标 bbox，规则校验兜底。
4. **重训 OTA**：合并新样本重训 yolov8n → 导 ONNX → 更新 assets。

#### 6.5.2 记谱规则（ChineseNotation）

## 8. 关键术语速查

| 术语 | 含义 |
| :-- | :-- |
| canonical | 透视校正后的规整棋盘图坐标系（450×500，带 MARGIN） |
| file / rank | 列(0..8) / 行(0..9)，rank 0 黑方底线(顶)、rank 9 红方底线(底) |
| 物理棋盘边 | 棋盘木板的外边缘（SAM 掩码给出） |
| 网格线交点 | 最外层网格线相交点（比物理边内缩 MARGIN=25px） |
| 单应 H | 平面间透视映射（8 自由度），4 组点对应求解 |
| DLT | 直接线性变换，求解单应的标准方法 |
| DSNT | 软 argmax 关键点解码（角点模型的坐标输出头） |
| negamax / alpha-beta | 极小极大搜索的负值最大化形式 / 剪枝优化 |
| UCCI | 中国象棋引擎通用通信协议 |
| FEN | 局面记谱（Forsyth-Edwards Notation） |

## 9. 决策记录（一句话回顾「为什么现在是这样」）

1. 棋盘定位：Hough 和角点模型都因斜拍/域差失败 → 选 **SAM/EdgeSAM 分割**（零样本，~3–4px）。
2. 棋子识别：整盘分类因域差失败 → 定为 **YOLO-nano 逐子检测**，训练数据用**自动标注**（方法 D：运动 + 开局引导 + 规则传播），绕开合成域差。
3. 引擎：先用纯 Kotlin 跑通闭环（M7 已达成）→ **换 XQWLight（Java 移植版，UCCI 协议，GPL-2.0，2026-10-06 已落地）** 提升棋力；因本机无 NDK/CMake，弃「NDK/JNI」改 Java 移植版（同算法/同棋力）。
4. 架构：接口隔离 + 工厂，所有模块可替换（换模型/引擎只改工厂一行）。
