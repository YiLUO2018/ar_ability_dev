## 2026-10-07：OCR 读字验证（结论：通用模型不可行，单字分类器暂缓）

探索「用开源文字识别辅助确认棋子身份」，验证后放弃通用 OCR，单字分类器记入备选方案暂不执行。

### 验证（`tools/label_real/ocr_piece_spike.py`）
用 RapidOCR（PP-OCRv6 rec，PaddleOCR 的 ONNX 版，无 paddle 依赖、CPU 可跑）读「已知框 → warp → crop」后的单字 patch：

| 测试对象 | 读对率 |
|:--|:--|
| 合成印刷体单字（黑体白底，11 个象棋字） | 11/11 = 100% |
| board_21（480×640 小图，38 子） | 0/38 |
| debug_video_01 frame500（1080p，标准开局 32 子） | 3/32 ≈ 9% |

穷尽优化：原方向/180° 旋转、48–128 尺寸、灰度 CLAHE/Otsu/自适应阈值/形态学去噪、简体+繁体字表，读对率仍 ~9%。

### 结论
- **根因 = 域差**：PP-OCR 训练的是「印刷体简体」，真实棋子是「书法体繁体（馬/車/將）+ 薄墨低对比 + 木纹 + 斜拍」，同类域差（角点合成失效、Swin 0.83）。
- 通用 OCR ~9% 连「辅助确认」都不够（需 ≥60–70%），**放弃**。
- **备选 = 自训 11 类单字分类器**（正视角单字输入，架构比 YOLO 简单、更抗域差），但天花板 = 标签质量，与 YOLO 同源；等 M3/M4 视频规则传播能稳定出「准身份标签」再启动。详见 `真实数据自动标注方案.md` §12。

### 决策
回到 **数据飞轮验证优化**（真机采集 → 离线标注 → 重训 → OTA），OCR/单字分类器暂不投入。

### 关键设计
- **标准开局身份当 teacher（standard 模式）**：单帧离线标注只能对「确为标准开局」的帧免费拿到 32 子身份（`match_standard` 多子拒绝、缺子≤2 补齐）；中局帧需 M3/M4 视频规则传播，单帧标不了身份 → 跳过。
- **YOLO-in-the-loop（yolo 模式，突破「只能标标准开局」）**：`metadata.detections` 里的端上 YOLO 原始框**只当身份提案，不当真值**——SAM 定位置、YOLO 提身份、规则/判色/置信度当裁判，三关全过才落标签，冲突跳过记 `review.jsonl`。这样不会自循环（规则是最终权威）。
- **yolo 模式已知局限**：车/马/炮（无位置约束）与同侧象/马的单帧身份无法用规则裁决，仍继承 YOLO 的域差；这类帧会因冲突被跳过，需 M3/M4 视频传播（运动定身份）或人工 review。
- 类别顺序与端上 `YoloPieceDetector` 一致：0–6 红 帅/仕/相/车/马/炮/兵，7–13 黑 将/士/象/车/马/炮/卒（已用 `match_standard` 验证 32 子 14 类计数正确）。

- `match_standard(STD_OCC)` → 32 子，14 类计数 = {帅1 仕2 相2 车2 马2 炮2 兵5}×2，`class_id` 映射与 14 类契约一致。

## 2026-10-06：接入 XQWLight 引擎（Java 移植版）

按用户拍板的「引擎 → 数据飞轮 → 其他」顺序，落地引擎替换（第一优先）。

### 决策变更：NDK/JNI → Java 移植版
原定 XQWLight NDK/JNI，但环境检查发现：本机 SDK **无 NDK、无 CMake、无 cmdline-tools/sdkmanager**，且本地无 C++ 源码。经用户确认，改用 **XQWLight 官方 Java 移植版**（同作者、同算法、同棋力、GPL-2.0），免 NDK/JNI。

### 已完成
| 文件 | 说明 |
|:--|:--|
| `xqwlight/Position.java` | XQWLight 官方源码（局面 + 走法生成 + 评估），保留 GPL 头 |
| `xqwlight/Search.java` | 迭代加深 + 置换表 + 空着裁剪 + 静态搜索 |
| `xqwlight/Util.java` | RC4 哈希 / 排序 / 二分等工具 |
| `chess/XQWLightChessEngine.kt` | `ChessEngine` 实现：`Board.toFen → Position.fromFen` + `searchMain(64, 1000ms)` + `mv` 解码回 (file,rank) |
| `chess/ChessEngineFactory.kt` | 返回 `XQWLightChessEngine()`（`KotlinChessEngine` 保留为降级） |

### 桥接要点
- FEN 约定完全一致（k/a/b/n/r/c/p，黑小写/红大写，rank0=黑方底线在顶），直接喂 `fromFen` 即可。
- 走法编码 `src + (dst<<8)`，`src=file+3+((rank+3)<<4)`；解码回 `file=(sq&0xf)-3`、`rank=(sq>>4)-3`。
- XQWLight 本质「限时迭代加深」，`bestMove` 忽略 `depth`、用固定 1s 时间预算（约深度 8–12，远超原 Kotlin 深度 3）。

### 遇到的问题与解决
1. **根节点无合法走法崩溃（AI OOBE）**：XQWLight `searchRoot` 在 `mvResult=0` 时仍调 `setBestMove(0,…)`，`historyIndex(0)` 算出负下标越界。修复：桥接层先用 `board.generateMoves` 判空，无合法走法直接返回 null（符合接口契约）。单测 `xqwLightEngineNoMovesWhenMated` 覆盖。

### 验证
- `./gradlew :app:assembleDebug` 通过（Java + Kotlin 混编正常）。
- 单测 10/10 通过，含新增 `xqwLightEngineReturnsLegalMove`（校验返回走法 ∈ 合法走法集、不污染入参局面）。

### 下一步（数据飞轮，第二优先）
端侧采困难帧 → 自动标注 → 重训 YOLO（覆盖跨场景域差，§6.5.1）。

### 真机调试发现（关键）
1. **棋盘定位掩码选择 bug（已修）**：SAM 返回 4 个候选掩码，棋盘木板与桌面同色时会把掩码「溢」到桌面（溢出掩码 35–50% 画面 > 正确棋盘 12–24%）。旧代码无条件选「面积最大」→ 选中溢出掩码 → 超面积上限报「无棋盘」。**修复 = 在合法面积区间内挑最大**（跳过超限溢出候选），见 `SegmentationBoardDetector`。
2. **提示工程救不了溢出（实测）**：加 8 边框负提示点 → 掩码 52%（更糟）；加 4 上一帧四角正锚点 → 50%（更糟）。棋盘/桌面边界对比太低，SAM 分不开；正解是选掩码而非改提示。
3. **YOLO 跨场景域差（待数据飞轮）**：定位稳定后 YOLO 逐子 ~80–90% 正确——象/马/将混淆、少量漏检，单视频训练覆盖不了新棋盘。

把「真实照片自动标注」落地为 `tools/label_real/` 的几何精修模块，解决合成→真实域差。方案见 `docs/真实数据自动标注方案.md`。

### 已完成

|:--|:--|

| `tools/label_real/lines.py` | Canny + HoughLines 直线检测 + 水平/垂直分族 + rho 聚类 |

| `tools/label_real/validate_synthetic.py` | 合成数据量化验证（扰动粗角点 → 精修 → 对比 GT） |
| `docs/真实数据自动标注方案.md` | 方法 A（SAM 粗定位）/ B（几何精修）/ C（时序投票） |

### 方法（refine_corners）
1. 粗 4 角 → 初始单应 H（canonical → image）。
2. rectify 到正对棋盘（解决棋盘任意倾斜问题）。
3. 直线检测（高 Hough 阈值滤掉棋子/文字伪线）→ 匹配 canonical rank/file → 交叉出节点。
4. `cv2.findHomography(RANSAC)` 拟合残差单应 D，`H ← H@D` 迭代。
5. 质量闸门：grid_rms 没变好则回退粗角点。

### 验证结果（合成 640×640，扰动粗角点）
- 粗角点噪声 10px（≈模型实际输出）→ 角点误差 **降约 26%**（11.7px → 8.7px）。
- 理想（0px）→ 下限约 1.6px（镜头失真 + 检测噪声）。
- 噪声 20px+ → 收益有限（略变差，闸门回退）。

### 遇到的问题与解决
1. **`cv2.getPerspectiveTransform` 要求 float32**：geometry.py 里误传 float64 → 断言失败，改为 float32。
2. **棋盘倾斜时 `split_hv`（固定 0°/90°）失效**：最初在图像空间直接分横竖线，倾斜棋盘（~41°）几乎检不到线 → 改为**先 rectify 到正对**再做直线检测。
3. **Hough 阈值过低导致聚类失败**：阈值 80 时棋子边缘/文字伪线污染聚类，网格线位置错乱；阈值 ~140 时才能干净检出 10 横 + 9 竖。
4. **粗角点带噪声时残差是投影变换**：等距网格拟合（offset+k*spacing）在残差含透视时发散 → 改为「节点 → 完整单应」RANSAC 拟合。
5. **密集棋子 + 楚河汉界 + 镜头畸变**：网格线被遮挡/打断/弯曲，Hough 检测精度 ~2~5px，未达亚像素。

### 遗留 / 下一步
1. 亚像素直线检测（LSD / 投影剖面亚像素拟合）+ 镜头畸变标定，突破 ~1.6px 下限。
2. 接入 SAM 粗定位（方法 A）缩小 ROI、去除棋子干扰。
3. 方法 C（棋子时序投票 + 合法性）待阶段 2 整盘分类输出。
4. 真机采集 → 全自动标注 → 混合微调。

## 2026-10-02：真机调试 — 修复棋盘定位

真机验证时发现棋盘检测失败（画面无黄色外框）。通过把检测器输入帧与边缘图落盘分析，定位到两个根因并修复。

### 根因
1. `GridBoardDetector.houghLines` 的非极大值抑制（NMS）存在坐标不统一 bug：比较「原始 rho 索引」与「rho 值（已减 diag）」两个不同量纲，导致 `tooClose` 恒为 false、NMS 完全失效，单帧产出 3.5 万个伪峰值，min/max 取角被噪声污染。
2. 分类阈值 `SIN_THRESHOLD=0.7071`（45°）过宽，棋子圆边等斜向边缘被误判为横/竖直线，污染直线集合。

### 修复
- 修复 NMS：统一在「原始 rho 索引」坐标系内比较，抑制后再转换为 rho。
- 收窄方向带：横线 84°–96°、竖线 0°–6°/174°–180°，过滤斜向噪声。
- 增加票数过滤（保留 ≥ 最高票 45% 的直线）与贴图像边界的伪直线剔除。
- 修正直线位置计算（取图像中心列/行处的 y/x），替代 `rho/sin`、`rho/cos` 的近似。

### 验证
- 真机出现黄色棋盘外框（透视梯形，正确框住棋盘，外框下方为木色桌面、内部为棋盘）。
- 「下一步」可触发走子建议（系统 Toast 出现）。

### 遗留
1. 棋子识别（模板匹配）为占位实现，准确率低，需替换为 TFLite 15 类分类模型。
2. 棋盘定位仍需在更多光照/角度下微调；后续接 OpenCV（设计文档阶段二）提升鲁棒性。
