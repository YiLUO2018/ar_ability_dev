## 1. 共同设计基座

两侧共享同一核心思想链：**SAM 掩码分割 → 四角拟合 → 单应（canonical 450×500）→ 90 交点**。

两个贯穿性约定：

- **坐标语义**：SAM 掩码给出的是**物理棋盘边四角**，warp/单应目标是 `BoardGeometry.physicalCorners`（[0,0]–[450,500]），网格交点自然落在 `(MARGIN+f·50, MARGIN+r·50)` = `(25+f·50, 25+r·50)`。
- **选型依据（失败史）**：角点回归模型（合成→真实域差，置信度虚高）与 Hough 原图定位（斜拍竖线偏 7–17°）均已证死路，SAM 分割是唯一稳定入口（~3–4px）。证据见 `03-探索与调研/棋盘定位方案探索记录.md`。

两侧差异由约束决定：**端侧受实时约束**（轻量 EdgeSAM + 时间滤波闭环），**标注侧无实时约束**（重模型 + 迭代精修 + 局面先验）。

## 2. 端侧实现（`chess/SegmentationBoardDetector.kt`，~900 行）

### 2.1 模型与推理

| 项 | 内容 |
|---|---|
| 模型 | EdgeSAM 3x（ONNX：encoder 22MB + decoder 16MB，onnxruntime-android 1.22） |
| 预处理 | resize 长边→1024 保比例 → RGB (v−mean)/std → 右下补零 NCHW（对齐官方 `Sam.preprocess`） |
| encoder | `image`[1,3,1024,1024] → `image_embeddings`[1,256,64,64] |
| decoder | embeddings + `point_coords`[1,1,2] + `point_labels`[1,1]（点提示，初始 0.5/0.5，成功后回灌）→ `scores`[1,4] + `masks`[1,4,256,256]（logits，阈值 0） |
| 线程 | intraOp = CPU 核数 clamp [2,8]；纯 CPU（XNNPACK） |

### 2.2 单帧 detect 流水线

```
bitmap
 ① 面积带过滤：每候选二值化→最大4邻接连通域面积，须在 [2%, 35%] 掩码画布内
     └ 上界挡「溢出到桌面」掩码，下界挡棋子/碎块（按分数选会被 1.0 分碎块骗）
 ② 逐候选提四角 extractCornersEx：
     连通域→边界像素→凸包→
     ├ 优先外推复原 reconstructClipped（角点出画面时）
     └ 否则 simplifyRing（删垂距<2.5px 栅格毛刺）+ 贪心减点到 4 顶点
 ③ 掩码坐标→原图坐标，isValidQuad 非退化校验（两点距≥2%对角线、面积≥1%画面）
 ④ 两轮优先级：先「全可见」（贴边 8px 内=被裁切，拒），后「外推复原」（允许出画±半幅）
 ⑤ 同优先级时间稳定性仲裁：取与上一帧四角平均位移最小者
 ⑥ 跳变闸：面积比 [0.75,1.35] + 角位移≤0.22×对角线；跳变需连续 3 帧一致才放行
 ⑦ 提示点回灌：四角质心（复原态用可见掩码质心）clamp [0.02,0.98]
 ⑧ 自适应 EMA：α=clamp(dist/(diag×0.08), 0.15, 0.9)——小位移强平滑、大位移快跟随
 ⑨ buildInfo：warp 到 canonical + 产出 imageToGrid 单应
```

各闸门针对的实测失败模式：

| 闸门 | 挡什么 | 实测来源 |
|---|---|---|
| 面积带 [2%,35%] | 棋子碎块（score 可 1.0）；溢出桌面超集（35–50%） | 10-04 / 10-06 真机 |
| 时间稳定性仲裁 | 面积带内但四角逐帧乱跳的溢出掩码 | video_02 f170-f210 |
| 跳变闸 0.22 | 单帧滑落 283px 的偶发坏角（旧阈值 0.30 恰好放过） | v7 f185 TR 角 |
| isValidQuad | 掩码噪声产出的两点重合/细条退化四边形 | PC 复刻回放 |

### 2.3 外推复原（角出画面，P3 核心增量）

凸包环上「两端点都贴内容边界（容差 4px，掩码坐标）」的段 = 裁切痕迹，整段丢弃；剩余可见边线按环序合并近共线链（弦方向夹角 cos>0.94，含环形接缝合并）后须恰 4 条 → **相邻边线延长求交 = 四角**（允许出画面 ±半幅）。覆盖 1 角/2 对角出画；整条边出画无解返回 null。

三个实测坑（必记）：
1. 贴边判据必须用掩码**内容边界** nw/4,nh/4——非方形输入的 256² 画布右/下是 letterbox 零填充；
2. 须先 `simplifyRing`（贪心删垂距<2.5px 顶点）——栅格阶梯毛刺在角点产生 26°/45° 碎折点，共线合并跨不过；
3. 贴边容差 ≥4px——真实解码器上采样掩码距内容边界有 1~3px 内缩（真机 fail 掩码实测 2px），1.5px 判不到裁切痕迹。

复原态提示点用可见掩码质心（四角质心可能已在画面外）。

### 2.4 QuadRefiner（棋子质心反馈精修，P0-b）

**动机**：掩码近端常「溢」到桌面/阴影条带 → 底部节点系统性偏低 → 棋子被就近吸到上一行（红底线 8/9 颗跑到 rank8，即 B1 问题根源）。

```
≥12 个 YOLO 质心 → 就近吸附交点(≤0.8格) → RANSAC 500 iter 拟合校正单应
  防退化三闸：① 唯一性内点计分（每质心至多贡献一个内点，拒秩2退化解）
             ② 内点 ≥16 且行列覆盖各 ≥6
             ③ 单角校正量钳制 ≤1.5 格（是精修不是重检测）
→ refineQuad 经同一套 isValidQuad/isCutOffQuad/跳变闸校验后融入 EMA
```

与离线 `fit_std_homography.py` 同思想（质心当锚点）；端侧因有定向网格，**无 180°/镜像翻转歧义**。

### 2.5 性能现状

| 指标 | 数值 | 备注 |
|---|---|---|
| 单帧延迟 | ~1s（V2509A CPU，encoder 主导） | 有效闭环 ≈0.7–1Hz，跟随慢的根源 |
| 角点原始精度 | 3–4px 级（参考 ViT-B 基准） | 圆钝角系统性内缩（见 §5 Q4） |
| 长期稳定性 | 真机 45s 无 fail；v9 验证角出画整段 0 失败 | |
| 支撑下游 | YOLO round 吸附（格 50 canonical px） | 几 px 角差足够 |
| 已知短板 | ① ~1s 延迟 ② 极端斜角连败段（v9 后 81 帧）③ B1 近端半行吸附（QuadRefiner 缓解未根除） | |

## 3. 自动标注侧实现（`tools/label_real/`，PC CPU）

无实时约束，按数据源/场景分**三条并存路径**：

### 路径 A：SAM ViT-B 直接分割（静态真机帧，`test_sam.py`）

点提示 → multimask 3 候选 → `findContours` 最大轮廓 → `approxPolyDP` 多 eps（0.01→0.05）4 顶点 → `order_quad`。精度 **~3–4px**（vs 人工修正 GT），ViT-B CPU 单帧 ~8s。选型验证脚本 + M0 逐子分割底座。

### 路径 B：几何精修链（`refine.py` + `m1_intersections.py` / `m3_refine_board.py`）

SAM 物理四角（输入）→ 物理角转网格角（内缩 MARGIN）→ **refine_corners 迭代精修**（6 轮）：

```
rectify 正对 → Canny+Hough 找横平竖直线（20px 门槛剔外框线）
→ 1D rho 一对一匹配 canonical 位置 → 横×竖线交点 = 节点对应
→ findHomography RANSAC(6px) → 乘入 H
质量闸：grid_rms 精修后没变好就整体回退粗角
产出：grid_rms / n_nodes / ortho_deg / aspect 四个质量分
```

**已知失效模式**：暗桌面掩码溢出时 refine_corners 会**自洽锁错线组**（rms=1.35 看着很好却全错）→ grid_rms 不能当唯一质量闸（诊断利器 = warp 后 90 交点 grayMin 网格 + ASCII 渲染）。SAM 拟合四边形略大于真实棋盘边 → 网格整体偏 ~13 canonical px、压缩 ~8% 的系统偏差（残留 25px 偏移问题在待办）。

### 路径 C：棋子锚定 RANSAC（`fit_std_homography.py` + `video_label_std.py`，标准开局视频主路径）

路径 B 全挂时的正解——SAM 逐子分割的**质心与节点分配无关、始终可靠**：

```
SAM 粗四角（允许偏 1–2 格，面积带 [10%,60%]）
→ detect_pieces 质心（逐子点提示，~50s/帧 CPU）
→ 对应无关 RANSAC（4000 iter）：32 个标准开局 canonical 位置 ↔ 质心
    防退化三重：粗糙节点 ±1 格邻域构造候选对（恒等对 70% 偏置）
              + 唯一性内点计分（每检测点至多贡献一个内点）
              + valid_h（四角投影面积 ≥16 格²）
→ 内点数 ≥28 = 同时解出 H 与「确为标准开局」验证
→ 180° 翻转歧义：墨色红度差（每子笔画最暗 25% 像素的 R-G，红方位−黑方位）
    绝对阈值判色全灭，相对判别才有区分度（实测 +0.286 vs −0.286）
    弱信号(|gap|<0.05) 继承上一帧方向；镜像歧义无害（开局左右对称）
```

**扩展（`video_label_yoloassist.py`）**：极端斜角帧粗四角偏差超 ±1 格邻域 → 候选对构造必败。改用 **PCA 粗对齐**（两团点主轴 8 种符号/换轴组合估计旋转/平移/尺度，自动覆盖 180° 翻转）构造候选对；YOLO 只贡献几何锚点、身份仍由 std 先验出（无自证循环）。回收 34/50 跳帧。

另：`replay_pipeline.py` 在 PC 忠实复刻端侧 EdgeSAM 全链（面积带/外推复原/时间仲裁/EMA/跳变闸），是端侧算法的离线回归测试床（~0.5s/帧 vs 端上 ~1s）。

## 4. 两侧对照总结

| 维度 | 端侧 | 自动标注侧 |
|---|---|---|
| 分割模型 | EdgeSAM 3x（轻量，~1s/帧） | SAM ViT-B（重，棋盘 ~8s、逐子 ~50s/帧） |
| 四角提取 | 凸包+贪心减点 / 外推复原（手写几何） | approxPolyDP（OpenCV）+ 三路径各异 |
| 精度手段 | 时间滤波：面积带→时间仲裁→跳变闸→自适应 EMA→QuadRefiner 反馈 | 空间精修：rectify+Hough 迭代（refine_corners）或先验 RANSAC（标准开局 32 子锚点） |
| 防退化机制 | isValidQuad / 面积带 / 唯一性内点 / 校正钳制 | 唯一性内点 / valid_h / grid_rms 回退（有自洽锁错风险） |
| 出画处理 | 外推复原（实时） | 基本拒帧（粗四角须全在画面内） |
| 实测精度 | 3–4px 级 + 闭环校正，支撑 round 吸附 | ViT-B 3–4px；精修后 grid_rms ~0.8–1.4 canonical px |
| 主要失败模式 | 暗桌溢出（压制未根治）、极端斜角连败、~1s 延迟 | refine_corners 自洽锁错线组、非标准开局帧无身份源 |

**架构呼应**：QuadRefiner（端侧）是 fit_std_homography（标注侧）的「无标准开局先验」移植版——同一思想（质心锚点 + 唯一性内点 RANSAC）两侧各自演化，标注侧的退化单应教训直接写进了端侧代码注释。

## 5. 讨论记录

### Q1：warp 的必要性在哪里？（2026-10-10）

区分两个概念：**warp 图像**（透视校正成 450×500 位图）vs **canonical 坐标系**（`imageToGrid` 单应，交点固定在 `(25+f·50, 25+r·50)`）。

当前消费方核查结论：**坐标系必要，图像已接近遗留**。

| 消费方 | 用什么 | 地位 |
|---|---|---|
| YoloPieceDetector（主路径） | 原图 crop + imageToGrid 单应吸附 | 不用 warp 图 |
| BoardOverlayView | imageToGrid 单应画箭头 | 不用 warp 图 |
| TFLitePieceRecognizer（兜底） | boardInfo.warped | 用 |
| TemplatePieceRecognizer（兜底） | boardInfo.warped | 用 |

warp 图的历史必要性在 v1 整盘 TFLite 分类器（透视/尺度归一后 90 交点固定，逐格采样确定性强、无 NMS）。切 YOLO 主路径后识别改在原图做（避免重采样损失小目标细节）。**本质必要的是 canonical 坐标系**：图像点↔(file,rank) 是一次 3×3 矩阵乘法，吸附/overlay/记谱/飞轮元数据全建立其上。

工程观察：`buildInfo` 在 detect 与 refineQuad 各 warp 一次（全图 getPixels + 450×500 重采样），主路径不用 → 可改 lazy 生成，每帧省两次位图重采样。

### Q2：运行频率与后端，能否上 GPU？（2026-10-10）

- **频率**：CameraX KEEP_ONLY_LATEST + 单线程 executor；`DETECT_EVERY_N=5` 才跑检测+识别。名义 6Hz，实际单次 EdgeSAM ~1s + YOLO 串行同线程 → **有效闭环 ≈0.7–1Hz**，瓶颈是单次耗时不是抽样间隔。
- **后端**：纯 CPU（ORT 默认 XNNPACK，仅设了 intraOp 线程数）。
- **GPU 路径**：① `SessionOptions.addNNAPI()` 一行可试，但 ViT 算子（LayerNorm/attention）NNAPI 支持参差、逐算子 fallback 回 CPU 可能反而更慢，且 NNAPI 自 Android 15 已弃用——须真机实测；② TFLite GPU delegate 需自转（官方无 TFLite，链路长）；③ 厂商 NPU（QNN 高通较成熟，联发科 APU 无官方 ORT EP）。
- **更划算的加速（不动后端）**：降输入分辨率 1024→512（ViT 计算量约平方降，~4×）；四角锁定后降频跑 encoder（中间帧 decoder-only 或纯几何跟踪，失败/跳变再全量重检——同时是 P2 IMU 落地场景）；fp16 配 GPU 才明显。

### Q3：面积带过滤合理吗？（2026-10-10）

**作用域澄清**：面积带不是「从画面找棋盘」的检测器，而是在点提示已打在棋盘上的前提下，对 SAM 的 4 个粒度候选（子部件/物体/超集）做初筛。实测分数不可靠（碎块 score 可 1.0）。

- 下界 2% 挡碎块/棋子；上界 35% 挡溢出——关键：**溢出掩码也是合法四边形**，isValidQuad 拦不住；时间仲裁首帧/重锁时无历史，面积上界是唯一防线。
- **合理性评估**：是「手机举在棋盘上方一臂距离」的场景先验，非通用检测器。局限：贴近拍摄棋盘真实占比 >35%（掩码画布约 >46%）会被误杀；分母是 256² 画布（含 letterbox 填充）而非图像内容，阈值语义随横竖比漂移。
- **更原则性的增强**：用几何先验替代纯面积——四角单应投影到 canonical 后量测 aspect≈450:500、对边长度比、内角（透视容差下）。不依赖拍摄距离，成本 O(1)。误杀兜底：全候选被拒每 10 次落盘 fail 诊断帧。

### Q4：先提 4 条边再求交得角点？（2026-10-10）

**思路正确，且已实现一半**：外推复原路径（reconstructClipped）正是「环分段→近共线合并→恰 4 条边线→延长求交」；全可见路径用的是凸包+贪心减点、角点取自凸包顶点。

提边求交理论上更准的原因：SAM 掩码四角圆钝（圆化几 px），凸包顶点落在圆弧上系统性内缩；直边段长且干净，延长求交能穿过圆角交出真实角（离线 refine.py 同哲学——在图像空间找真实线而非掩码边界）。

全可见路径未用的原因：① 手遮挡会截断/弯曲边线，共线聚类会把一条边拆两条，需鲁棒拟合；② 无「贴边痕迹」先验辅助分段，要纯几何聚类；③ 下游容差大（round 吸附格 50px + EMA），3–4px 级偏差无感。

**演进方向（若攻 B1）**：把复原路径的边线求交推广到全可见（simplifyRing → 共线聚类 → 恰 4 链求交，失败回退贪心减点），改动集中在 extractCornersEx，Python 侧 `test_geom_reconstruct.py` 同款单测护航。

### Q5：掩码是什么？（2026-10-10）

**掩码 = 像素级归属图**：SAM decoder 对 256×256 每位置输出 logit，>0 即属于提示所指物体。与 bbox 对比：掩码贴合物体真实形状。

在本链路被消费五次：① 连通域面积（候选评分）② 边界像素序列→凸包→四角 ③ 质心（提示回灌 + QuadRefiner 锚点）④ 贴边痕迹（外推复原的裁切证据）⑤ 离线：逐子掩码→bbox→YOLO 训练标签。

选分割作定位入口的原因：棋盘是大幅面平面物体，掩码外沿即物理边，四角可几何导出；对斜拍/光照/纹理鲁棒（角点回归与 Hough 已证死路）。

### Q6：TFLite 整盘分类是在做什么？（10-10 第二轮）

v1 架构的识别器，现为二线兜底（工厂优先级 YOLO → TFLite 整盘 → 模板）：
- 输入：warp 规整棋盘（450×500 canonical）缩 0.8×（360×400）；
- 模型：合成数据训练的 CNN，输出 [1,15,10,9] logits——90 交点各一个 15 类分布（空+红7+黑7），逐点 argmax 出 10×9 网格；
- 优点：一次前向出整盘、无 NMS、逐格位置天然对齐；死因：① 合成域差 ② 把识别精度**绑死在 warp 精度**上（warp 偏一点、90 交点采样全偏）。YOLO「原图检测+单应吸附」解耦了这两者。
- 它是 warp 图仅存消费方之一——其退役即 C1（warp lazy 化）可落地之时。

### Q7：模板匹配的模板是什么？能否反向 warp 模板？（10-10 第二轮）

- 模板 = **程序渲染**的棋子灰度图（renderTemplate：米黄圆饼 + Android 默认粗体汉字，红/黑），每 Piece 一张按 cellSize 懒生成；匹配 = warp 图逐交点 ROI → 占用检测（背景差>60 占比>30%）→ 红黑判色（R 通道占优>30）→ 7 字形 NCC 取最大。
- **反向 warp（模板变形到原图）可行**：每交点用 H⁻¹ 局部仿射近似变形模板后在原图 NCC。优点：避免整图 warp 插值损失（远端小目标拉伸模糊）。但：① 该识别器死因是**模板域差**（渲染字形≠真实字体+光照），换 warp 方向救不了；② 90 点逐点变形比一次整图 warp 贵；③ v0 冷启动遗产不值得再投。
- 思想的现代对应物已存在：YOLO 在原图 crop 上跑（不做透视校正）、overlay 是坐标级 warp。若复活模板路径，正确姿势 = 从 SAM 逐子掩码抠**真实棋子**建模板库 + 逐点局部变形。

### Q8：GPU 加速——MNN+OpenCL/Vulkan、ncnn+Vulkan（10-10 第二轮）

比 NNAPI 更认真、比自转 TFLite 更现实的两个选项：
- **ncnn**：Vulkan 成熟；官方 examples 有 **MobileSAM 端侧 demo**（encoder+decoder），SAM 系跑通有先例；
- **MNN**：OpenCL/Vulkan 双后端，transformer/attention 算子覆盖好（手机端 LLM 部署主流）。
- 移植成本（vs addNNAPI 一行）：两模型 ONNX 转换（decoder 点数固定 N=1）→ 逐张量精度对齐 → C++ JNI 桥 + 前后处理移植（当前 ORT 纯 Java）。
- 路径：① addNNAPI 真机实测（零成本先排除）② PC 转换 + benchmark 估收益（encoder ViT fp16 GPU 经验 ~2–4×）③ ≥2× 才上真机。与 C2 正交可叠加，组合预期 8–16×（encoder ~900ms → 60–100ms 量级）；decoder 轻，留 CPU 避免 kernel launch 开销。

### Q9：面积带之外，用棋盘内容（网格/棋子）验证候选？（10-10 第二轮）

方向正确——给候选掩码加语义/内容验证，三层按成本递增：
1. **质心包含率**（近零成本，运行时）：复用 MainActivity 已有 lastCentroids（YOLO 质心），统计落在候选掩码内的比例——真棋盘应包含几乎全部质心。有历史时可用，恰好补齐面积带管不到的运行时场景。
2. **网格线验证**（首帧/重锁强闸）：候选四角 warp 到 canonical → Canny+Hough 数横平竖直线对 canonical 命中数（期望 9 竖 10 横）。离线 grid_rms 思想端侧化；溢出掩码 warp 后网格缺失/错位即露馅。~10–30ms/候选，仅无历史时跑。
3. **几何先验**（C4）：aspect/内角/对边比，与内容验证互补。
原则：优先做**排序信号**而非硬拒（闸门越多误杀类别越多）；fail 诊断落盘保留兜底。

### Q10：掩码质心是什么？（10-10 第二轮）

- 定义：掩码内全部前景像素坐标平均（一阶矩/重心）。与四角质心的区别：四角质心=顶点平均，角点出画时可能在画外；**掩码质心始终在可见像素内**。
- 两个"质心"各自的作用：① **棋盘掩码质心** → decoder 提示点回灌（复原态用，:181-185）；② **棋子质心**（YOLO 框中心 / SAM 逐子掩码质心）→ QuadRefiner 与离线 fit_std_homography 的 RANSAC 锚点、M3 跟踪。
- 可靠性根源：全像素平均（噪声误差 ~1/√N）+ 与角点拟合/节点分配**完全解耦**（四角提取失败不影响质心）——"质心当锚点"哲学的根基。

### Q11：不考虑时间与算力，数据侧还有哪些优化点？（10-10 第二轮）

四类（优先级序）：
- **A 标注能力**：① M3/M4 运动传播落地（中局身份标注钥匙，乱摆静态帧无解）② teacher 升级 SAM ViT-H/L（权重本机已有 vit_l 1.2GB / vit_h 2.5GB）或 SAM2（时序一致）③ 多模型 ensemble + 分歧帧挖掘（active learning）④ review.jsonl 复核工具化、fail 诊断帧入标注链。
- **B 数据多样性（B2/B3 直击）**：⑤ 多棋盘/光照/机型采集（当前域窄是 v10 主瓶颈）⑥ 远端小目标颜色专项 + 黑方视角扩充。
- **C 监督形式**：⑦ mask 级监督训 yolov8n-seg（SAM 掩码在手却只用外接 bbox）⑧ 渲染合成小目标混合正则（10–20%）⑨ hard-example replay。
- **D 评测体系**：⑩ 固定诚实 val（防泄漏虚高）+ 真机回归集脚本化（每轮自动出 32/32 率/身份准确率/假阳率，替代人工看回放）。
- 提醒：数据侧真正稀缺的是**新场景采集与人工复核时间**，不是算力。

### Q12：TFLite 整盘分类 / 模板匹配可以取消吗？（10-10 第三轮）

**都可以，建议取消**：
- 两者唯一触发条件是 YOLO ONNX 加载失败（工厂 catch 链）——模型打在 assets 里，加载失败=构建损坏，此时兜底毫无意义；
- 即使触发，真机质量也不可用（TFLite=合成域差；Template=渲染字形域差）——**静默降级到不可用识别器比显式报错更糟**；
- 单测零引用，删除无负担。
- 建议连同相邻死链一次清理（见 §6 C8）：+ KeypointBoardDetector/board_corner.tflite、GridBoardDetector、tensorflow-lite 依赖（−3~5MB APK）、BoardInfo.warped（C1 从 lazy 化升级为彻底移除）。护栏：工厂失败显式报错，不静默降级。

### Q13：端侧 GPU 三方案验证与实施（10-10 第三轮，详见 §8）

本机已完成的前置验证：① encoder/decoder 算子清单（encoder 无 MatMul，RepViT Conv-heavy 移动友好；decoder 动态形状重 → 留 CPU 只挪 encoder）② PC CPU 基准（encoder 350–650ms 主导，与端上 ~1s 一致）③ **MNN 转换链路跑通**（mnnconvert --fp16 → 11.1MB，发现当前 encoder 是 fp32）。结论：**A NNAPI 半天先排除 → B MNN 主推（Java API 免 JNI，2–4× 预期）→ C ncnn 备选**；统一 bench harness + 决策门槛（≥1.5× 且角点 diff ≤2px）。与 C2 正交可叠加至 8–16×。

### Q14：IMU 完整方案（10-11 第四轮，详见 §9）

用户判断（降检测频率/提渲染精度）成立，再推两步：① 本质是**渲染与检测解耦**（overlay 从 ~1Hz → 30fps 相机帧率）② **IMU 预测 + 视觉 LK 微校正 + EdgeSAM 重置**三层架构（IMU 漂移/无平移 → 视觉校正互补）③ 重检测定时改**事件触发**。分阶段 T1 纯视觉传播（无传感器、PC 可 A/B）→ T2 IMU rotation-only 融合 → T3 平面分解全单应 + 传播角反哺检测器闸门 + box prompt + YOLO 频率解耦。

### Q15：网络视频数据闭环（10-11 第四轮，详见 §10）

用户骨架（端侧初检 → 高精度复检 → 校验 → 差则入库）正确，五个增强：①**失败归因先于入库**（模型/几何/选择三类，只有模型失败才训）② 分歧挖掘（active learning）代替全量回标 ③ teacher 自带质量闸（几何闸 + 双 teacher 一致性 + 标准开局 RANSAC 仲裁）④ **单应重放增强**（teacher 验证帧 + 随机单应 = 免费无限监督，专造极端角/出画样本）⑤ 按视频切分 + 端到端回归指标。

### Q16：微调 EdgeSAM 会提升吗？（10-11 第四轮，详见 §10.3）

条件性会：可改善圆钝角/特定溢出/提示鲁棒性，但 ① 下游容差大（3-4px 已够吸附），端到端收益取决于归因中模型失败的占比 ② 灾难性遗忘风险 → 冻结 encoder 只调 decoder + 混 10-20% 通用 SAM 数据 ③ 标签必须掩码级（teacher 供给），勿走角点回归头（= 已死方向 B）④ **零训练替代先试**（box prompt/C7/C5 治同一批症状）。顺序：归因 → 零训练手段 → decoder-only 微调 → holdout 回归。预期边界 3-4px→1-2px，端到端 detect 率 +0~10%。

### Q17：视频闭环对棋盘检测的收益校准（10-11 追问，详见 §10.4）

**结论：当"考场"用必赚（基准/归因/压力测试/负样本），当"教材"喂棋盘检测大概率亏——训练红利应优先喂 YOLO。** 结构性原因：棋盘检测瓶颈不在"见过的棋盘不够多"（基础模型的长板恰是泛化），而在对比度边界 + 后处理算法 + 延迟；且网络视频多为转播俯拍（比手持斜拍容易），真正的难例分布已由飞轮覆盖。四步走：现有视频先归因 → 网络视频只做半闭环（Stage 0-3 不训练）→ 训练预算给 YOLO（B2/B3 真饥饿）→ 归因显示掩码失败占比高才启动棋盘微调。

## 7. 边线求交提角（C5）实施方案

### 7.1 目标与范围
- 全可见路径用「4 条边线最小二乘拟合 + 相邻求交」替代「凸包 + 贪心减点」，消除 SAM 掩码圆钝角的系统性内缩（合成圆角 r=4px 时凸包顶点偏 ~2–3px，边线求交 <0.5px，交点天然亚像素）。
- 改动收敛在 `extractCornersEx` 全可见分支；外推复原路径已是边线求交，不动。
- **诚实预期**：px 级精度改进 + 为更精细的时间仲裁打底，**不是 B1 的解药**（B1 是掩码溢出致节点整体下移 ~0.5 格/25px 量级，归 QuadRefiner 管）。

### 7.2 算法步骤
1. `simplifyRing`（现有，eps=2.5px 去栅格毛刺）；
2. 顶点转角检测：逐顶点计算局部方向变化角，>阈值（初始 30°）处断开 → 环分成若干链（比外推复原路径的「近共线合并」更主动的分段）；
3. 每链最小二乘直线拟合 + 拟合 RMS：RMS 超阈（弯曲/遮挡边缘）→ 该链不可靠；
4. 链数仲裁：>4 时短链（弧长 <0.5 格）并入邻链/丢弃重并；仍 ≠4 或有链不可靠 → **整体回退贪心减点**（保证不劣于现状）；
5. 恰 4 链 → 相邻直线求交 = 四角；
6. 后校验不变：isValidQuad / isCutOffQuad / 时间仲裁 / 跳变闸 / EMA。

### 7.3 风险与回退
| 风险 | 对策 |
|---|---|
| 手遮挡 → 凸包出现假边/链数错乱 | 链数 ≠4 或短链异常 → 自动回退贪心减点 |
| 镜头畸变大 → 边缘弯曲 | 拟合 RMS 闸 → 回退 |
| 行为回归 | 常量开关 EXTRACT_MODE（LINE_INTERSECT / HULL_VERTEX），可一键切回 |

### 7.4 验证与分阶段
- **P1 Python 原型**（零真机成本）：replay_pipeline 加开关实现同算法；test_geom_reconstruct.py 扩展合成单测（圆角 r=2/4/6px + 阶梯毛刺掩码，断言边线求交误差 < 凸包法）；对 debug_video_01/02 回放 A/B，指标：QuadRefiner 唯一内点数、检出中位数、>32 帧占比、角点轨迹平滑度。
- **P2 Kotlin 移植**：extractCornersEx 加 extractCornersFromLines（保序 fallback）；ClippedQuadReconstructTest 加同款合成用例。
- **P3 真机验证**：log 角点 diff、吸附率、B1 红底线 rank8 复现率对比。

## 8. 端侧 GPU 加速三方案：验证结果与实施方案（2026-10-10）

> 目标：encoder（~1s，占 detect 耗时主导）挪到手机 GPU；decoder 留 ORT CPU。
> 当前 adb 无设备连接，上机实测待手机接上后按本节协议执行。

### 8.1 已完成的前置验证（本机）

| 验证项 | 结果 | 结论 |
|---|---|---|
| encoder 算子清单 | Conv 130 / Add 104 / Mul 66 / Div 29 / **Erf 27**(GELU) / **ReduceMean 14**(LN) / Relu 10 / Sigmoid 10 / Pow·Sqrt·Sub·Resize 6，共 475 节点，**无 MatMul** | RepViT 重参数化、Conv-heavy，移动 GPU 友好；但 Erf/ReduceMean/Div 散布各 block，NNAPI 分片存疑 |
| decoder 算子清单 | 34 种算子，Shape 107 / Gather 105 / Unsqueeze 103 动态形状逻辑重 | 转换痛苦且仅占 ~10–15% 耗时 → **不转，留 ORT CPU** |
| PC CPU 基准（WSL 8 线程） | encoder@1024 ≈ 350–650ms；decoder ≈ 140–200ms | 与端上 ~1s 比例一致，encoder 是唯一目标 |
| MNN 转换链路 | Windows `mnnconvert -f ONNX --modelFile encoder.onnx --fp16` → `enc_test.mnn` **11.1MB 转换成功** | 方案 B 前置打通；**发现当前 encoder 是 fp32（22MB），fp16 直接减半** |
| NNAPI/ncnn 上机 | 未做（无设备 / 需 NDK 与预编译包） | 按下述方案执行 |

### 8.2 共同基座：端侧 bench harness（先建，三方案复用）

`MainActivity` 加 bench 模式：`adb shell am start -n …/.MainActivity --ez bench true --es ep cpu|nnapi|mnn`：

```
30× encoder（同一 bitmap）+ 20× decoder + 20× 全链 detect()
logcat tag=BenchEP 输出 p50/p95；写 filesDir/bench_<ep>.txt 供 adb pull
```

**统一决策门槛**：encoder p50 加速 ≥1.5×，且 10 张参考帧角点与 CPU 基线 diff ≤2px，且 500 次迭代无崩溃/泄漏 → 采纳。看 p95（热节流）不只 p50。

### 8.3 方案 A：NNAPI（0.5 天，先做先排除）

- 改动：`opts.addNNAPI()`，session 创建 try/catch 回退 CPU；`setLogLevel(VERBOSE)` 抓节点分片日志。
- 预判：Conv/Add/Mul/Relu/Sigmoid ≈ 320/475 节点友好；Erf/ReduceMean/Div/Pow/Sqrt ≈ 72 节点回退且与 Conv 交错 → CPU↔NPU 乒乓搬运可能吃掉收益。**成功率中低，成本半天**。
- 判据：bench 对比 + 分片日志中 NNAPI 节点占比 <50% 基本可判死。

### 8.4 方案 B：MNN + OpenCL/Vulkan（2–3 天，**主推**）

- 主推理由：① 转换已验证（§8.1）② 官方 Java API（mnn-java aar）**免手写 JNI**——只替换 `runEncoder()` 内部，预处理/decoder/后处理全不动 ③ Conv 图的 OpenCL 支持成熟。
- 步骤：
  1. 获取 MNN Android SDK 预编译 aar（github 直连受限走镜像/代理，或 WSL 源码编译）；
  2. `enc_test.mnn` 入 assets；写 `MnnEncoderRunner`：load → session 配 `MNN_FORWARD_OPENCL`（失败回退 VULKAN/CPU）+ fp16 → 喂 float[] → 读回 embeddings；
  3. `runEncoder` 加后端开关（ENC_BACKEND：ORT_CPU / MNN_GPU）；数值对齐：同输入与 ORT CPU 比 embeddings max|Δ|（fp16 下 1e-2 量级正常）；
  4. bench ep=mnn 上机，按 §8.2 门槛裁决。
- 预期：中端 SoC OpenCL/Vulkan fp16 对 Conv 网 **2–4×**；模型 22MB→11MB。
- 风险：GPU 驱动碎片化（kernel 编译慢/失败，回退链必留）；fp16 精度（角点 diff 闸把关）。

### 8.5 方案 C：ncnn + Vulkan（3–5 天，备选）

- 前置障碍：本机无 NDK（自编译需先装）；预编译包走 github release（直连受限）；C++-first 需自写 JNI 桥。
- 参考资产：ncnn 官方 examples 有 **MobileSAM 端侧 demo**（encoder+decoder 全链先例）。
- 建议：仅当 MNN 实测 <1.5× 或驱动问题频发时投入。

### 8.6 执行顺序与组合

```
bench harness（0.5 天）→ A NNAPI 实测（0.5 天，大概率排除）
→ B MNN 集成上机（2–3 天，主预期 2–4×）→ 视结果决定 C
全程与 C2（512 重导出/降频）正交可叠加，组合上限 8–16×：encoder ~1s → ~100ms 量级。
```

附注：C2 的 512 重导出需从官方 EdgeSAM PyTorch 做（pos_embed 插值随输入尺寸变，不能只改 ONNX 维度）；当前 fp32→fp16 的 MNN 模型已顺手完成。

## 9. IMU / 帧间几何传播完整方案（2026-10-11）

> 扩展并取代 `01-现行设计/跟踪-IMU-引擎优化方案.md` 的 P2 草案（rotation-only v1）。
> 核心思想：**IMU 粗预测 + 视觉微校正 + EdgeSAM 重置** 三层各司其职；
> 本质收益 = 渲染与检测解耦（overlay 从 ~1Hz → 30fps）+ 重检测事件触发。

### 9.1 架构与分阶段

**T1 纯视觉传播（无 IMU，PC 可离线 A/B，先行）**
```
检测成功 → 记录 90 网格节点反投原图的像素位置（强角点跟踪窗口）
每相机帧 → LK 光流跟踪（金字塔 2 层，~几 ms）→ RANSAC 帧间单应 ΔH → 传播四角
         → overlay 30fps 渲染；YOLO 用传播 BoardInfo 吸附
检测时刻 → 重置跟踪点（消漂移）
```
- 可在 replay_pipeline.py 实现并 A/B；误差度量无需 GT：重检测时「预测角 vs 检测角」位移即天然误差。

**T2 IMU rotation-only 融合**
```
TYPE_GAME_ROTATION_VECTOR（无磁干扰）→ 只取增量 ΔR = R(t2)·R(t1)ᵀ（设备系，不积绝对姿态）
时间戳对齐：sensor ts(ns) ↔ ImageProxy.imageInfo.timestamp，帧间线性插值   ← 命门，错位=反向补偿
设备系→相机系固定旋转 + 内参 K（LENS_INTRINSIC_CALIBRATION 常缺失 → fx=fy≈帧宽、主点居中）
像平面传播：ΔH_img = K·ΔR·K⁻¹（任意 3D 旋转通用，不限绕光轴）
融合：IMU 粗预测 ∘ LK 残差最小二乘微校正
```

**T3 完整形态**
- 平移补偿：上次检测单应 Zhang 分解取正对棋盘解得平面法线 n、距离 d；帧间 ΔH = K(R + t·nᵀ/d)K⁻¹。
- **传播角反哺检测器**：prevCorners 用传播角——时间仲裁/跳变闸/自适应 EMA 目前假设棋盘准静态（运动下把真实移动当抖动平滑掉），传播角做参考后运动场景才正确。
- **box prompt**：detect 时用传播四角外接框做 decoder box 提示（两点+label 2/3）——压制暗桌溢出的零训练手段。
- **YOLO 频率解耦**：几何靠传播保鲜，YOLO 独立 2–3Hz，不与 EdgeSAM 绑同一节拍。

### 9.2 新组件与验证

- 新增 `chess/BoardTracker`（onDetect / onCameraFrame / onImu → currentCorners）；MainActivity 注册 sensor；overlay 改吃 tracker 输出。
- 门槛：预测 vs 检测角位移 **p50 < 8px、p95 < 25px**；重检测间隔延长 2–4×；箭头钉板主观评分。
- 风险：时间戳错位（反向补偿，比不补更糟）；rolling shutter 快速歪斜（v1 忽略）；磁干扰（增量法免疫）。

## 10. 网络视频数据闭环与 EdgeSAM 微调评估（2026-10-11）

### 10.1 闭环流水线（用户骨架 + 五增强）

```
Stage 0 摄入：帧哈希去重 / 模糊暗光质量闸 / 同视频限量（多样性）/ 保留部分无棋盘帧做负样本
Stage 1 端侧复刻：replay_pipeline（同算法）→ detect 结果 + 全部候选掩码 + 失败类型
Stage 2 teacher：SAM ViT-H/L(+ViT-B) + approxPolyDP + 几何闸(aspect/grid_rms)
                + 标准开局视频棋子锚定 RANSAC 仲裁 + 双 teacher 一致性分
Stage 3 分歧分级：角差 <3px → 回归数据；3px+ 或端侧失败但 teacher 有效 → 难样本；teacher 也挂 → 弃/负样本
Stage 4 失败归因（关键闸）：
   模型失败（teacher 掩码 vs 全候选 IoU 都低）→ 微调池
   几何失败（有候选掩码好但角提取差）        → 算法池（C5/C7），不入库
   选择失败（好候选被拒/选错）               → 仲裁调参池，不入库
Stage 5 训练/改进 + 固定 holdout 视频集端到端回归（detect 率/角误差/溢出率/复原率）
```
- 切分纪律：train/val **按视频切**（v3 泄漏教训）。
- **单应重放增强**：teacher 验证帧 + 随机单应变换 = 标签按变换精确更新的免费无限监督，专造极端斜角/角出画样本（练外推复原），零版权零采集。

### 10.2 与既有资产的关系

数据源 = 网络视频（新增，域广）+ 飞轮 775 帧真机难帧 + std02 + m5 清洗集；标注侧三路径（§3）中路径 A/C 直接复用，路径 B（refine_corners）仅作 teacher 候选不自洽时参考（grid_rms 不能当唯一闸）。

### 10.3 EdgeSAM 微调评估（Q16 详版）

| 维度 | 判断 |
|---|---|
| 可改善 | 掩码圆钝角（边界锐化 → 角点精度）、特定背景对溢出、单点提示鲁棒性 |
| 前提 | **归因显示模型失败为主**（否则白训）；标签必须掩码级（teacher 供给） |
| 防遗忘 | 冻结 encoder 只调 decoder（16MB）或 LoRA；混 10–20% SA-1M 通用数据 |
| 禁忌 | 角点回归头 = 已死方向 B 换皮（合成域差教训），走 mask 路线保架构 |
| 零训练先行 | box prompt（§9 T3）/ C7 内容验证 / C5 边线求交——治同一批症状，一周内可落地 |
| 预期 | 边界 3–4px → 1–2px 可期；溢出率视训练覆盖；端到端 detect 率 +0~10% |
| 训练环境 | WSL GPU（YOLO 同款）；EdgeSAM 官方蒸馏训练代码可改监督微调 |

### 10.4 收益校准：闭环对棋盘检测值不值（10-11 追问）

**结论：非训练收益（考场）确定，训练收益（教材）有限且应让位给 YOLO。**

| 短板 | 数据闭环 | 备注 |
|---|---|---|
| 极端斜角连败段 | 不确定 | 归因未知（掩码坏 vs 选择/几何失败），先归因再谈数据 |
| 暗桌溢出 | 部分能 | 微调可学低对比边界，但 box prompt（§9 T3）是零成本替代 |
| 边界圆钝 3–4px | 能但无感 | round 吸附格 50px，传导不到端到端 |
| 角出画 | 不需要 | 外推复原已 0 失败 |
| ~1s 延迟 | 不能 | 工程问题（C2/C6），与数据无关 |
| 换棋盘泛化 | 名义能、存疑 | 基础模型长板恰是泛化 |

结构性原因：瓶颈不在"见过的棋盘不够多"，在对比度边界 + 后处理算法 + 延迟；网络视频多为转播俯拍（比手持斜拍**容易**），真难例分布已由飞轮 775 帧覆盖。B1/B2/B3 全在 YOLO/几何侧——**同样一批视频喂 YOLO 期望收益显著更高**。

确定的非训练收益：① 多样化回归基准（每轮改动跑 detect 率/角误差/溢出率/复原率）② 负样本 gating 校准 ③ 后处理压力测试（暴露 C5/C7/外推复原的算法 bug）④ 微调池储备。

投入顺序：**现有 debug_video_01/02 先跑归因（零新数据，验证方法论）→ 网络视频半闭环（Stage 0-3 不训练）→ 训练预算给 YOLO → 归因显示掩码失败占比高才启动棋盘微调**。

## 11. 收尾总结：优化点全景与执行路线（10-11 定稿）

### 11.1 五组优化点

**快赢组（≤1 天）**：C8 Legacy 清理（APK −4~6MB/净删 ~1500 行/warp 彻底移除）｜C3 NNAPI 实测（含 bench harness 搭建，三 GPU 方案复用）｜C7① 质心包含率（近零成本）｜C4 几何校验替代面积带（O(1)）。

**精度与鲁棒组（一周内）**：C7② 网格线验证（首帧/重锁强闸）｜C5 边线求交提角（§7：消圆钝内缩至亚像素，非 B1 解药）｜box prompt（治溢出的零训练手段，弱化版可用上帧四角）。

**性能工程组（攻 ~1s 延迟）**：C6 MNN+OpenCL/Vulkan（主推，fp16 模型已转换就绪，预期 2–4×）｜C2 降分辨率/降频（~4×，需 PyTorch 重导出，与 C6 叠加上限 8–16×）｜ncnn 备选（仅 MNN 不达标时）。

**架构升级组**：C9 BoardTracker（T1 视觉 LK → T2 IMU → T3 完整；overlay ~1Hz→30fps 钉板、事件触发重检测、EMA/仲裁运动语义修正、YOLO 频率解耦）。

**数据与评测组（考场优先）**：C10a 现有视频归因（零成本首步，决定后续数据投入方向）｜C10b 网络视频半闭环（基准/负样本/压力测试，不训练）｜C10c EdgeSAM 微调（条件触发：归因显示掩码失败占比高；训练预算优先 YOLO）。
